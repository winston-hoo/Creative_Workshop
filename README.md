# 小说创作工坊 · 本地工作台

给**网络长篇小说**（长篇连载那一路）用的一套本地工具。两条主线：

- **拆别人的书**：导入 → 切分 → 逐章标注 → 实体统计 → 大纲 / 知识库 / 体检报告。目的是**学结构**——钩子怎么轮换、情绪怎么起伏、伏笔隔多少章回收、人物什么时候退场。
- **写自己的书**：创作台的三层真源（设定集 → 分卷目录 → 逐章创作指令）→ 逐章起草正文 → 按技法维度审稿，审出来的问题落回指令，再重写。

自己的书和别人的书用**同一套分析**：等 `90-draft/` 里攒出定稿章节，走一次录入就能把自己写的书也纳进结构体检。

两条硬约束不是可调参数：**作品原文与密钥不出本机**（只绑 `127.0.0.1`）、**文件系统是唯一真相源**（没有数据库、没有内存缓存）。实现位置见下文「[两条硬约束](#两条硬约束)」。

## 哪些操作花钱

只有真调模型的那几处花钱，其余全是本地计算。每个花钱操作**执行前都会弹确认框**，把范围、token 与预估费用列清楚。

| 花钱 | 说明 |
|---|---|
| 逐章标注 / 批量标注 | **主成本**。全书 token × 单价 |
| 实体统计 | 唯一需要**再读一遍全本**的步骤（人物关系的细节只存在于正文） |
| 大纲 | 吃标注产出的梗概，分块归约。933 章约 20 次调用 |
| 改写台 | 一章一次调用 |
| 创作台 | 设定集助手、写正文、技法审稿，各一次调用 |
| 探测 P1–P5 | P5 约 2000 token；「测试连接」只发合成测试文本，极小 |

| 零成本（纯本地） | 说明 |
|---|---|
| 导入、切分、清洗、重建核验 | 纯脚本 |
| 脚本轨字段 | 字数、段落、对话占比、人称、风格违规，全是正则 |
| 伏笔台账 | 只在本地文件上记账 |
| 知识库 K1/K2/K3 | 聚合标注与实体，不调模型 |
| 结构体检报告 | 现读文件现算 |
| 题材库聚合 / 对比分析 / 融合器 | 原料是各作品的 `k3-fingerprint.json`，纯脚本 |
| 技法库 | 只是读 Markdown |

## 打包成 exe（给不装 Python 的人用）

**不装 Python 的机器不用自己打包**：到仓库的 `Releases` 页下载 `CreativeWorkshop.exe`，双击即用。
exe **不进主分支**——二进制进了 git 就永久留在历史里，每重打一版仓库就涨一份体积。
它由 CI 在发版时自动构建并挂到 Release 附件上，工作流见 `.github/workflows/release-exe.yml`
（发布 Release 自动触发；也可以在 Actions 里手动运行并指定要附加到哪个标签）。

要自己打一份、或改过代码之后重打：

```bash
python -m pip install --user pyinstaller
python build_exe.py
```

产物是单个文件 `dist/创作工坊.exe`（约 17 MB，目标机器不需要装 Python）。
双击即用：起本地服务 → 自动开浏览器 → 关掉那个控制台窗口即停。

**数据不放在 exe 旁边，而是放 `%LOCALAPPDATA%\创作工坊`**。首次启动自动铺一份
`providers.yaml` / `primitives.yaml` / `work.yaml` 模板，**已存在的文件一律不覆盖**——
用户改过的配置比模板重要。源码方式运行仍然用项目目录，行为不变。

端口默认 8765，被占用时自动换一个空闲端口，而不是启动失败。`--no-browser` 可以不开浏览器。
**只绑 127.0.0.1 这条在 exe 里同样成立**——它写在 `launcher.py` 的常量里，不是命令行参数。

单文件模式每次启动都要先解包到临时目录，比源码启动慢几秒，这是单文件换来的代价。

## 两条硬约束

| 约束 | 实现位置 |
|---|---|
| **探测不发送任何作品原文** | `probe.py` 里的测试句全部是内置合成文本，逐字固定 |
| **密钥绝不进日志与报告** | `secrets.py` 的 `RedactingFormatter` 挂在日志出口统一脱敏；报告写入前也过一遍 |

第二条特别说明：模型调用失败时，很多 SDK 会把请求头打进错误栈，而错误栈会写进日志。
所以不能只靠「我们没打印它」，必须在**出口**做统一脱敏。

## 探测与基准测：怎么用

### 先自检（不花钱、不需要密钥、不涉及作品数据）

```bash
python probe_cli.py --self-test
```

自检会启动一个本地模拟的 OpenAI 兼容服务，把 P1 到 P5、基准测、报告落盘、
对比告警整条链路跑一遍，并**断言判定逻辑是否正确**，而不只是「能不能跑通」。

还可以验证两条降级路径：

```bash
# 模拟模型不支持结构化输出 —— 应标记为不支持，但仍可启用
python probe_cli.py --self-test --mock-no-json

# 模拟响应不返回用量字段 —— 费用只能估算，但仍可启用
python probe_cli.py --self-test --mock-no-usage

# 模拟无流式 —— 应测不到首字延迟，其余正常
python probe_cli.py --self-test --no-stream
```

**降级场景下服务商仍然应该可启用**，这是自检验证的重点：探测失败不等于不可用，
只等于使用方式不同。

### 看配置里有什么

```bash
python probe_cli.py --list
```

### 不变式检查（另有独立脚本）

```bash
python tests/test_invariants.py
```

检查的是最要命的两件事：**密钥不泄漏**、**错误分类正确**。这两条一旦破了，
后果不是「功能不对」而是「安全事故」，所以单独成一份不依赖测试框架的检查脚本。

覆盖：脱敏替换、未知密钥形态拦截、日志出口脱敏、**报告落盘前后端脱敏**
（模拟上游错误体夹带密钥的场景）、密钥来源优先级、8 类 HTTP 状态码分类、
非阻断错误的语义。

### 真实探测（手动「测试连接」）

```bash
# 先把密钥放进环境变量，不要写进任何文件
export DEEPSEEK_API_KEY=...        # Windows PowerShell: $env:DEEPSEEK_API_KEY="..."

python probe_cli.py --provider deepseek
```

探测只在手动执行时触发，不在保存配置时自动跑。**每一次探测都是你有意识的行为。**

### 常用参数

| 参数 | 说明 |
|---|---|
| `--model` | 指定模型，省略时按 `probe_model` > `main` 角色 > 首个模型 |
| `--samples` | 采样次数，默认 3，取中位数（单次延迟波动大） |
| `--text-chars` | 测试文本的中文字符数 |
| `--chapters` `--concurrency` | 填上待处理章数与并发数，顺带推导全量耗时 |
| `--no-stream` | 关闭流式，会测不出首字延迟 |
| `--no-archive` | 只在屏幕看，不落盘 |
| `--no-compare` | 跳过与上一次的对比 |

## 探测做了什么

| 项 | 内容 | 成本 |
|---|---|---|
| P1 | 端点与鉴权 + 模型列表（重复采样测往返延迟） | **零** |
| P2 | 基础对话（流式，测首字延迟与总延迟） | 极小 |
| P3 | 结构化输出是否支持 | 小 |
| P4 | 响应是否返回 usage（**费用能否实测取决于它**） | 零，复用前面响应 |
| P5 | 中文 token 换算系数，**两点法**差分消掉固定提示词开销 | 约 2000 token |
| P6 | 并发上限 —— **明确不探**，按控制台配额手填 | — |

**为什么 P6 不探**：要试到触发限流才知道，有成本也有触发风控的风险；而且供应商配额
按账号等级分级，实测值换账号就失效。查控制台更省事也更准。

### 推导值

基准测不只记录数据，还把它翻译成可直接用的配置值：

| 推导值 | 公式 |
|---|---|
| `suggested_timeout_sec` | 中位总延迟 × 3，向上取整 |
| `est_single_chapter_sec` | 首字延迟 + 500 输出 token ÷ 实测速度 |
| `est_full_run_hours` | 单章耗时 × 章数 ÷ 并发数（需提供参数） |

**这就是基准测最直接的产出**：把「超时 60 秒」这类拍脑袋的默认值，
换成这台机器、这条网络、这家服务商实测出来的值。

## 报告与对比

报告存到 `config/probe-reports/`，同时写一份 YAML（机器读）和一份 Markdown（人读）。
**保留历史不覆盖**——没有历史就没有退化监测。

`index.json` 汇总所有报告，支持三种对比：

| 对比 | 用途 |
|---|---|
| 同一服务商跨时间 | 退化监测，新报告自动与上一次比 |
| 跨服务商 | 选型 |
| 同家不同模型 | 档位选择 |

### 可比性前提

对比前会校验 `prompt_hash`（测试配方指纹）。**测试句或采样参数改过，历史数据就不可比**，
此时会拒绝直接对比并说明原因，而不是给出一个看起来合理但错误的结论。

两次探测的计费时段不同（一个高峰一个空闲）时允许对比，但会标注时段差异——
峰谷不只影响价格，高峰时段的负载也可能不同。

延迟变化超过阈值（默认 ±50%，见 `providers.yaml` 的 `alert_on_change_pct`）时给出告警，
文案包含可能原因与建议，而不只是一个数字。

## 创作台：三层真源

**做什么**：从零写一部长篇，设定会散在 Word、聊天记录和脑子里，写到第 30 章名字就开始漂，第 4 章之后再没露面的配角也没人发现。创作台把「必须稳定、改一次就连累几十章」的东西收进一份手填的 YAML 设定集，再往下派生分卷目录和逐章创作任务指令：三层都落文件、人可读可改，模型只是可选的起草手段。

目录编号从 60 起（`60-setting` / `70-volume` / `80-brief` / `90-draft`），00–50 留给「分析已入库作品」那条链，这样同一部作品将来既可以是原创的，也能走标注、体检、知识库。`work.yaml` 里记 `kind: original`；原创工作区没有 `00-ingest`，标注那条链暂时跑不了（那些阶段要 manifest），等 `90-draft` 里攒出定稿章节，再走一次录入就能接上。

**用法**

```bash
python create_cli.py --new 关山灯 --genre 玄幻 --protagonist 李默 --core-motive "活着回去" \
    --logline "一个能看到数值的废柴，靠吐槽在修真界活下来。"
python create_cli.py --check 关山灯                   # 校验设定集
python create_cli.py --show 关山灯                    # 渲染人读版
python create_cli.py --show 关山灯 --inject 4000      # 打印真正喂给模型的那段设定卡
python create_cli.py --sync 关山灯                    # 主角/动机同步进 work.yaml
python create_cli.py --chain 关山灯                  # 三层链路体检（先看这个）
python create_cli.py --list                          # 列出所有原创工作区
```

`--root <目录>` 换工作区根目录，默认项目下的 `workspaces/`。`--new` 会把已知的书名、题材、前提、主角、动机直接写进骨架，随后打印下一串该跑的命令。

界面：书架点「新建原创作品」，填书名、题材、一句话前提、主角名、核心动机，创建后落到 `#/work/{name}/creation`。总览页最上面是「下一步」卡（① 设定集 → ② 分卷目录 → ③ 逐章创作指令）加三张可点的层卡，下面依次是全书梗概卡、角色动态卡、伏笔账本卡，左侧栏列设定集、各卷、各章。

进 `#/work/{name}/creation/setting` 写设定集，有「表单」和「原文」两种模式：表单保存会重新 dump YAML，文件头挂一句说明——手写注释会被覆盖，想留注释就切「原文编辑」；表单草稿是空的而磁盘上那份有内容时，保存会被拒绝，防的是读取出问题把文件清成 `{}`。

接口：`POST /api/creation/new`；`GET /api/works/{name}/creation`（三层完成度 + 逐卷逐章清单 + 梗概/角色/伏笔）；`GET|PUT /api/works/{name}/creation/{kind}?key=`（kind = setting / volume / brief；PUT 收 `text` 手写原文或 `data` 结构化，解析不了就不落盘）；`POST /api/works/{name}/creation/seed-briefs?vol=`。

**方法**

- **设定集只存一份**：`60-setting/setting.yaml` 是带注释、人手填的真源，不另存一份机器版。**为什么**：两份就会有一份先过期，而「设定集过期」是最难发现的一类错。新建时的模板带注释，并且把已知的书名/题材/前提/主角/动机直接填好，不留空让人再抄一遍——第一版必须能「打开就填」，否则写作者会退回去用 Word 写设定，设定集就又一次变成摆设。
- **校验分两档，不猜也不填默认值**：阻断项 = 缺了它会产出自相矛盾的目录或指令（缺一句话前提、`characters` 为空、`role=主角` 不是恰好 1 个、人物重名、非法的 `style.perspective`）；提示项 = 能往下走但多半漏了或前后不一致（人物 `faction` 不在 `factions` 里、关系指向不在 `characters` 里的人、`terms` 或 `themes` 为空、`target.chapters` 没填）。**不这么做会怎样**：替作者补一个默认值，等于把「他还没想清楚」伪装成「已经定了」。
- **注入块超预算不静默截断**：`render_injection_block` 按固定顺序注入，超上限就从后往前丢小节，并在末尾点名丢了哪几节；告警里报的是中文小节名（「人物」），不是内部 key（`characters`）——报 key 的话，人看到「characters 没注入」还得回去查代码。第一条「基本信息」永远保留：设定卡没有头部就没有意义，宁可超预算并**明说**超了，也不把句子拦腰砍断——半截设定比没有设定更坏。
- **主角与核心动机只有一处能改**：`work.yaml` 里的 `protagonist` / `core_motive` 由 `--sync` 从设定集抄过去。**为什么**：这两个字段是标注原语 P21 的度量对象，两处不一致，那一列数据就不可信。其余字段（`style_checks` / `ingest`）归 `work.yaml` 自己管，同步时不碰。
- **链路体检报完成度，不只报「有没有」**：`chain_report` 三层各自报进度，并且把「逐章指令只填了 3/100 章」也算成阻断。**不这么做会怎样**：一卷填满了、指令一份没写，检查下来是「没有阻断项」——而那时根本开不了工，是个假绿灯。
- **梗概是渲染，不是存储**：`render_synopsis` 每次从三层真源现算（含「已写正文 N/M 章」的进度），刻意不新增梗概字段。**为什么**：再存一份 300–500 字梗概就多出第三个真源，改一处另两处过期。
- **动笔前把真源渲染成输入**：`render_write_brief` 组装【全书锚点】【前情】【本段任务】【角色动态】【待回收伏笔】【章末钩子】【上一章末段】。锚点排在**最前**——放到当前文档之后就成「事后补充」，模型先看完几百字指令再看到它，就钉不住了；前情只到 `upto_chapter_no`，写第 3 卷时不把第 5 卷的卷末总结喂进去，否则它忍不住往那儿赶；锚点没有实质内容（只有书名）时返回空串，一个什么都没说的「锚点」只会占掉模型的注意力。
- **两道硬闸，闸只看指令**：`story_gates` 拦「主角连着 3 章没出场」（设定里标了多个主角就降级为提示，群像戏轮着来是正常的）和「上一卷没有卷末总结、下一卷也没有核心冲突」。人物出场只数逐章指令里的，不取卷表的并集——**踩过的坑**：卷表里写着主角、指令里没有，用并集的话闸永远不响。引导靠提示词，拦住必须靠代码。

**验证**

```bash
python tests/test_creation.py
```

16 组断言，不调模型、不需要密钥。跟这一层相关的覆盖：新建后四个目录都在、模板能解析、空设定集当场被拦、`work.yaml` 里写进了主角、重复建同一个工作区被拒；设定集校验的正反例（完整设定集零阻断零提示、势力对不上是提示、关系指向查无此人是提示、0 个或 2 个主角阻断、重名阻断、非法视角阻断、没有人物阻断）；主角/动机跟着设定集走、再同步一次不报变化、拼出的动机行对；注入块不超预算时无告警、超预算时出现告警并点名小节、报的是中文小节名、基本信息一定保住、先丢人物；空工作区链路不通、填完链路通；伏笔账本、人物动向与一致性（卷表里出现过的人也算、按缺席数排序、写成别名不再误报）、写前必读组装（锚点在最前、前情不剧透第 2 章、空作品返回空串）、硬闸的正例与反例（含群像降级）、段落任务进输入。

## 创作台：分卷目录

**做什么**：设定集管「不变的」，分卷目录管「怎么排」——卷 → 部分 → 章（章号 / 标题 / 内容概要 / 出场人物 / 伏笔动作）。一层一个文件：`70-volume/volume-001.yaml`，对标预案里的「第 N 卷 · 详细目录」。它也是逐章指令的唯一来源：卷表的章号、标题、概要就是播种的种子。

**用法**

```bash
python create_cli.py --check-volume 关山灯            # 校验全部卷（含跨卷衔接）
python create_cli.py --check-volume 关山灯 --vol 1    # 只看第 1 卷
python create_cli.py --show-volume 关山灯             # 渲染人读版
python create_cli.py --show-volume 关山灯 --vol 1
```

新建原创工作区时会顺手铺一份第一卷骨架（卷区间先按 1-100 起，填的时候改），省得去猜文件名和字段。`--check-volume` 打印每个文件读不出来的原因，以及「已填几卷、共几章」。

界面：`#/work/{name}/creation/volume/{卷号}`，卷号是数字，`1` 和 `001` 都能进；漏了卷号会自动补到第一卷。同样是「表单 / 原文」两种模式，表单里逐章表按行编辑，左侧栏列出已建的每一卷、并在卷名后面挂上这一卷有几项待修。助手起草在 `layer=volume` 下走（见设定集助手那一节）。

接口：`GET|PUT /api/works/{name}/creation/volume?key=1`；总览 `GET /api/works/{name}/creation` 的 `volumes` 行给出每卷的 `vol` / `title` / `start_chapter` / `end_chapter` / 章数与阻断数。

**方法**

- **章号连续性是这一层最强的信号**：本卷缺章、多出区间外的章、章号重复都算阻断，跨卷再查卷号连续、卷区间首尾相接。「第 3 卷少了一章」和「第 3 卷本来就只有 99 章」不靠连续性根本分不出来，所以报错也把后果写出来——「章号断档通常意味着有内容被悄悄漏掉」。
- **部分（`parts`）必须首尾相接、正好铺满整卷**：区间超出本卷、部分之间重叠或断档、第一部分不从卷首开始、最后一部分不到卷末结束，全是阻断。**为什么**：一卷铺一百章，不划部分逐章表就是一路平铺，看不出节奏；而区间不接续意味着中间有些章不属于任何部分，写那一段时没人知道它的任务是什么。**留空 `parts` 只是提示**，不阻断。
- **每一部分要写「必须完成的功能」**：`part_task_problems` 检查 `must_complete`，缺了给提示——光有一句「这一段讲什么」，写到第 5 章时没人告诉他任务达成了没有。`render_part_task` 会把它和 `ending_demand`（本段落点要求）一起渲染进写前必读，并说明本章是这一段里的第几章。
- **文件名与内容里的卷号必须一致**：`volume-003.yaml` 里写 `vol: 1` 会被当成「读不出来的文件」并说明两处不一致，改哪一处都得同时改另一处。读不出来的文件**不静默跳过**：那一卷当成不存在，会让「已经铺到第几章」这个结论悄悄变错，而人还以为只是少了一卷。
- **`--vol` 只看一卷，跨卷校验照跑**：指定卷号时只报这一卷自己的问题；不指定就逐卷校验一轮，再做一次跨卷校验（断档、重叠、卷号跳号、跟目标章数对账），一次看完。
- **单卷校验连卷头字段一起管**：`vol.vol` 没写或不是整数、缺 `start_chapter` / `end_chapter`、区间反了，都是阻断；卷名、`core_conflict`、`goal` 没写只是提示——「核心冲突」是分卷目录里最该写清的一项，但缺了照样能排章，不该卡住整条链。
- **这一层不接模型生成**：先把数据形状和校验定下来，形状对了才让助手进来。**为什么**：章表这种结构化程度高的东西，模型乱塞一行的破坏力比人设更大，所以助手那一层给它套了白名单 + 主键 + 整数三重限制，才敢让它动逐章表。
- **出场人物与伏笔动作都过一道闸**：逐章表里点名的 `characters` 要能在设定集里找到（找不到是提示，不是阻断——手打错字和名字漂移长得一样，而名字漂了是最难回头改的一类错）；`foreshadow` 只能填 `埋设 | 推进 | 回收` 或留空，填别的直接阻断。
- **跨卷校验顺带跟设定集对账**：`validate_chain` 拿 `target.chapters` 比一比，铺少了提示「还差 N 章」，铺多了提示超出多少。只查单卷的话，「目标 120 章、实际只排了 12 章」这种全局偏差没人看得见。
- **`--show-volume` 渲染的不是源文件**：逐章表按人读的表格排，划了部分就按部分分小节，没划就一张平表，卷末总结单独一段。**为什么**：人读版是给人看进度和查内容的，真源仍然是那份带注释的 YAML，两者分工明确。
- **编辑一卷时顺手体检邻卷**：保存卷层时，服务端把这一卷与磁盘上其它卷合并后再跑一次跨卷校验（`services._creation_validate_text`），所以改完立刻知道有没有把上一卷的结尾碰坏，不用来回切页面。

**验证**

```bash
python tests/test_creation.py
```

分卷相关三组断言：`test_volume_sequence_checks`（完整卷零阻断；缺一章被抓住；区间外的章被抓住；部分之间断档被抓住；部分没铺满整卷被抓住；出场人物不在设定集里给提示；非法伏笔动作阻断；缺 `gist` 阻断）、`test_volume_chain_checks`（两卷首尾相接通过；中间断档、区间重叠、卷号跳号各自被抓住；铺到的章数少于目标给提示）、`test_volume_files_roundtrip`（按卷号读回两卷；文件名与 `vol.vol` 不一致被拦住；渲染出卷标题、逐章表和按部分分的二级标题）。

## 创作台：逐章创作任务指令

**做什么**：一章一个文件 `80-brief/v001-c0001.yaml`，字段基准来自作者实际用过的「创作任务指令」：章节标题、核心情节、时间线衔接、字数要求、文笔要求、必须遵循的设定、上章遗留问题修正，外加伏笔动作、越界禁令和章末钩子类型。写正文的人（人或模型）只看这一个文件就该能动手，不必回去翻设定集和卷表。

**用法**

```bash
python create_cli.py --seed-briefs 关山灯                 # 按卷表播种全部缺的指令骨架
python create_cli.py --seed-briefs 关山灯 --vol 1          # 只播第 1 卷
python create_cli.py --check-brief 关山灯                 # 校验全部指令（含跨章伏笔引用）
python create_cli.py --check-brief 关山灯 --chapter v001-c0001
python create_cli.py --show-brief 关山灯 --chapter v001-c0001
```

`--vol` 不传表示不限卷；`--seed-briefs` 会打印新建了几份、跳过了几份，并明说「已有的文件一律不动——改过的指令不会被骨架覆盖」。

界面：总览页有「按卷表播种 N 章指令（不花钱）」按钮，左侧栏「逐章创作任务指令」下面一章一行、带「未填 / N 项 / 条数 / ok」的徽标，点某一行进 `#/work/{name}/creation/brief/{v001-c0001}`。章层除了指令表单，还有写正文面板（写这一章、读回正文、回填、技法审稿）。

接口：`GET|PUT /api/works/{name}/creation/brief?key=v001-c0001`；`POST /api/works/{name}/creation/seed-briefs?vol=`；`GET /api/works/{name}/creation/foreshadows`（伏笔账本）。

**方法**

- **章号沿用录入那边的编号约定**：`v{卷:03d}-c{章:04d}`。**为什么**：将来 `90-draft` 里攒出定稿章节，走一次录入，标注/体检/知识库那条链能直接接上，不用另起一套 id。文件名与里面的 `chapter_id` 必须一致，不一致算读不出来。
- **播种只抄不编**：`title` / `one_line` / 字数区间 / 视角分别从卷表和设定集抄下来，**已有文件一律不动**。**为什么**：这几个值手抄一遍就容易漂，而「指令和卷表对不上」正是这一层最该避免的错；覆盖策略更不行——改过的指令会被骨架抹掉。
- **指令必须能跟卷表对上**：`chapter_id` 说第 1 卷而 `vol` 字段写别的、或 `chapter_no` 对不上，阻断；章号不在那一卷的章表里，阻断并直说「卷表和指令对不上，二者必有一个错」；只有标题不一致才算提示——那多半是有一处改了没同步。
- **`core_plot` 空就是阻断**：没有核心情节，写正文的人只能自己编。`timeline` 缺了是提示——断在这里，正文会自己编时间；字数区间跟设定集的每章字数差到一倍以上（低于下限的一半或高于上限的两倍）也给提示，但不阻断，实验性的短章或长章是合理的。
- **伏笔编号：埋设时定号，推进/回收时引用**：引用一个先前没被埋过的编号，说明中途改过编号而后文没跟上；同一个编号埋两次，说明编号重用了。这种错只会在写正文时爆发，那时已经写完几十章，所以必须在这一层拦住。没写编号的埋设也拦——编号要在埋设时就定下来，后文才引用得到。
- **伏笔账本回答另一个问题**：链路校验只管「这一条回收得对不对」，`foreshadow_ledger` 管「现在还有几条挂着没收、挂了多少章」，按埋设章号排序。这里刻意**不重复**报链路校验的错——同一件事出现两遍，作者还得自己判断是不是两个问题。同一个 id 埋两次要点出来：后面的回收只关掉一个，另一个永远挂着，而作者以为它收了；回收之后又埋一次也要报，那是「以为收了，其实又开了」。
- **越界禁令和遗留问题各占一栏**：模板里留了 `must_not`（这一章**不能**写什么）和 `carry_over`（上一章留下的问题，这一章要修的那些：时间对不上、人物状态矛盾、承诺没兑现）。**为什么**：越界禁令比正面要求更能防跑偏，而遗留问题只会在下一章暴露，写进指令才有地方修。
- **模板是打开就能填的**：注释里对每一段都给了例子（核心情节按发生顺序一条一句、时间线接哪一章过了多久、伏笔编号自己定 F-001 这种），并写清校验命令。**为什么**：三层都是人写的真源，写作者不肯填，后面所有校验和生成都没有意义。
- **解析不了就不落盘**：保存前先解析再校验，解析失败把错误原样回给界面，磁盘上那份保持不动（三层一样）。**为什么**：存进去一份读不回来的文件，比拒收它坏得多——那份文件会一直躺在那里，直到生成阶段才发现。
- **章末钩子的十种类型写死在代码里**：`HOOK_TYPES` 是规范，校验和界面下拉框都靠它，所以它不能只躺在 `craft/hook-techniques.md` 里——改文档不影响校验，模型看到的钩子名就会跟校验认的对不上。连着两章用同一种类型要报：这防的是**写法重复**，读者说不清哪里腻，只觉得「怎么又是这套」；中间那章没填时不算连着两章。`render_hook_rotation` 还会把最近用过的四种和「本章不要再用哪一种」渲染进输入，并提醒填完把这一章的钩子类型写回去。

**验证**

```bash
python tests/test_creation.py
```

指令相关五组：`test_seed_briefs_never_overwrites`（播 12 份、标题/概要/字数/视角都是从上游抄的、第二次播种不新建且全部跳过、没填的骨架会被指出缺核心情节）、`test_brief_validation`（完整指令零阻断零提示；`chapter_no` 与 `chapter_id` 漂了被抓住；标题与卷表漂了给提示；章号确实在卷表里时不误报；不在了就阻断；`core_plot` 空阻断；字数区间反了阻断；视角与设定集不一致给提示；出场人物不在设定集里给提示；埋设/推进没编号阻断；非法伏笔动作阻断）、`test_brief_chain_foreshadow_refs`（埋设→推进→回收通过、引用未埋编号被抓住、同一编号埋两次被抓住）、`test_foreshadow_ledger`（挂着 1 条、收了 2 条、挂了几章算得对、重复埋设被点出、空目录返回 0 不报错）、`test_hook_rotation_and_part_tasks`（连着两章同一种要报、乱写的类型要报、轮换成功的不报、中间没填不算连着、只有缺 `must_complete` 的那一段要报）。链路体检那组还钉住了 ③ 层的两个数：计划 12 章、认出 12 份指令，骨架没填时链路仍然不通。

## 创作台：设定集助手

**做什么**：空白 YAML 对写作者并不友好。助手用对话起草三层文档（设定集 / 分卷目录 / 逐章指令），但形态是**提案制**：模型只返回「建议新增或修改哪几条」，界面把每条摊开，作者逐条勾选、勾中的进表单草稿，再自己点保存才落 `setting.yaml`。另有两个反向动作：**回填**（正文写完了，把正文里实际发生的事提回真源）和**技法审稿**（审出来的问题翻成对本章指令的修正）。

**用法**

界面上三步：

1. 在某一层的编辑页下方选素材档位（`none` 不注入 / `k3` 只注入结构指纹 / `full` 注入全部素材）和参照作品（只列建过知识库的已入库作品，没建库的勾不动），展开「看这次会喂进去什么」先看素材；助手卡上写着本次用哪个模型、预计多少输入 token、约多少元。

2. 写一句话（例：「给我三个配角——一个导师、一个对手、一个损友，都要有明确动机」）点「问助手（约 ¥x）」，或点「配齐…」勾类别加每类要几条、可加额外要求，一次提足。

3. 返回一张提案表（留 / 类别 / 动作 / 内容），「内容」可以直接改，改完的值覆盖模型原值；「接受勾选的」并进草稿，最后点保存才落盘。指令页还有「回填本章」和「技法审稿」两个入口。

接口：

```
GET  /api/works/{name}/creation/assist/plan?refs=&level=&layer=&key=&provider=&model=
POST /api/works/{name}/creation/assist        # 会花钱；只返回提案，不写任何文件
POST /api/works/{name}/creation/assist/apply  # 纯脚本；把勾中的并进草稿，不落盘
GET  /api/works/{name}/creation/kb/{ref}?section=&q=   # 翻已入库作品的知识库
POST /api/works/{name}/creation/kb-import     # 勾中的知识库条目转成提案；不调模型、不落盘
```

`layer` 取 `setting` / `volume` / `brief`，`key` 是卷号或章节号；`task=writeback` 走回填、`task=review` 走技法审稿，这两种情况下 `message` 不参与。

**方法**

- **提案制，不整份重写**：设定集是作者自己的东西。模型整份重写一遍，作者看完说「不是我想要的」，那次调用连同他的阅读时间全是无用功，而他刚手填的部分也被覆盖了——后者更坏。所以 `apply_proposals` 是这条链上唯一会写数据的地方，而且**模型说什么都不直接信**：不认识的小节、缺主键的条目、重名的角色一律拒收并写明原因，而不是塞进设定集当既成事实。它能脱离模型单测，这是刻意的：最容易出错的一段必须能不花钱地反复验。
- **白名单而不是黑名单**：`LAYER_SPECS` 逐层列出「你能动的位置」，路径相对于该层自己的文档。**为什么**：黑名单永远漏，而漏掉的那一项就是模型往里塞东西的口子。「多给了一个字段」看着无害，但它是静默污染——等发现时已经写了几十章，而那个字段谁也没定义过。
- **别名映射，但不放松白名单**：**实测踩过的坑**——卷表的「本章概要」字段叫 `gist`，模型反复写 `summary`，字段被丢掉，结果什么都没改却报「已保存」。这是最坏的一种失败：看着成功、实际空转，作者以为概要已经对齐了。所以加了 `aliases`（summary/desc/note → gist），而**映射之后仍然要落在白名单里**，映射到列表外照样丢；`update` 必须真的改到了字段才算成功，一条都没改到就拒收，并把模型给的字段名和允许的字段名都打出来。
- **整数字段必须转回 `int`**：`_clean_entry` 单独处理 `int_fields`，并且白名单要把 `int_fields` / 枚举字段 / 主键一起算进去。**踩过的坑**：只按 `fields` 算的话，章号会在转 `int` **之前**就被过滤掉，报出来的错是「缺必填 chapter_no」——明明作者给了章号；而章号真变成字符串「7」，卷表的连号校验当场崩，报的却是「缺 start_chapter」这种毫不相干的话，很难查回这里。
- **每一条都要有结果或原因**：逐条结果带 `ok` / `reason`，连「作者没勾选这一条」也记一笔。**不这么做会怎样**：勾了 5 条只进来 3 条，而作者只能怀疑是自己看错了。空壳提案（既没有 `entry` 也没有 `value`）直接拒，并把「模型实际给了什么」打出来。
- **三层共用一个引擎，白名单和提示词分开**：三层走同一条「提 → 逐条勾选 → 并入草稿 → 作者点保存」的路，差别只在 `LAYER_SPECS` 那张表和提示词的框架句。分卷目录和逐章指令一开始没有助手——「章表」这种结构化程度高的东西，模型乱塞的破坏力比人设更大，白名单 + 主键 + 整数三重限制之后才放它进来。同名小节靠层区分：`setting` 的 `characters` 是条目表，`brief` 的 `characters` 是字符串数组。
- **素材三档，默认 `full`**：这里**推翻了**早先一次实测的结论（那次同一问题各跑一次，全素材 2648 输入 token、不注入 636，产出「同等可用」，所以当时定了中间档 `k3`）。推翻的理由：那次测的是写三个配角，而 `k3` 只给统计量、零人名零势力零能力，而助手的主业恰恰是生成势力、能力、世界观——不给素材它只能凭空编，「知识库没起作用」就成了一句字面属实的话。样本各一次的结论撑不住这种代价；真要省钱的作者，界面上把档位调回 `k3` 就是（成本约为 `full` 的五分之一）。超预算时**点名丢了哪些小节**，不静默截断：素材少给一半，模型会自己补，补出来的东西跟参照毫无关系，而作者以为它是照着知识库写的。
- **借格局，不搬名字**：参照素材的提示明确要求借角色功能、势力格局、能力分层与节奏统计，不要把原作人名与专属名词直接搬进来——搬了是洗稿，而且一眼认得出出处。参照块只给素材不给名字串：人物带定位与身份、势力带立场、能力带效果，并按角色优先级排序，别让一个路人挤掉主角。
- **回填不是起草加几句话，是换一整套提示词**：起草是「从无到有提建议」，回填是「从既有正文里提取事实」，两条路混在一起必然出错。回填的铁律只有一条：**正文里没有的，一个字都不许提**；小节名必须带层前缀（`setting:abilities` / `volume:chapters` / `brief:foreshadow`）——`title` 在卷层和指令层都有，`characters` 在设定集是条目表而在指令层是字符串数组，光看裸名分不出指的是哪一个；只有**有名字**的人物、能力、地点、术语才值得提，一次性过场角色不要提；`volume:chapters` 只改本章那一行的概要，不许重排整张章表。
- **技法审稿不直接改正文**：机械自检查得了字数、禁令、漏人、截断，查不了「开头抓不抓人」「爽点结构完不完整」「有没有穿帮」，那靠技法库的审查维度。但产出是**对本章指令的修正**，不是改正文——正文是成品，模型改一遍等于重写，作者还得逐句对比；改成指令、再重写这一章，作者既看得见改了什么，也能否决。审稿还明确要求每条都指得出在正文的哪个位置，不接受「多加点细节」这种没法执行的建议。
- **知识库导入复用同一道闸**：不做「一键全收」，每条由作者点。它复用的就是模型提案那套（白名单、主键去重、逐条结果与原因），区别只有一个——提案不是模型生成的，是从 K1 实体表里读出来的。**导入路径如果比提案路径松，模型塞不进来的东西就能从这儿塞进来，两条路一个口子等于没有口子。** K1 里没有的字段（人物的「动机」）不编，留空由作者填：编一个占位符比留空坏得多，作者会以为那是从原作里读出来的。关系是嵌在人物里的数组，所以语义是 `update` 那一个人的 `relations`，**整条替换**而不是追加（追加的话同一个关系导两次就多一条，还和作者手改过的版本混在一起），并按（对象, 关系）去重——K1 的关系表按章累积，实测一个人有 3 条「师生」、5 条「师徒」。
- **先给数字再花钱**：`assist/plan` 不发起任何调用，只算出 token、费用和这次真正会喂进去的素材预览；没填单价就明说算不出，不给假数字。

## 技法库

**做什么**：给正文生成与审稿提供写作技法储备。内置 12 篇，`craft.py` 只做**检索与预算控制**——
按章号和本章指令挑几篇、拼成一段、超预算的点名，不改写原文一个字。

生成时技法跟设定集、本卷目录、本章指令拼进同一个提示词；审稿时换成另外两篇，走「技法审稿…」那条路，
输出的不是改好的正文，而是**对本章指令的修正提案**（正文是成品，模型改一遍等于重写，作者还得逐句比对）。

**用法**：

- **内置 12 篇**在 `src/workshop/craft/`，本项目自己写的，随仓库与 exe 一起走（`build_exe.py` 用
  `--add-data` 把整个目录打进 `workshop/craft`）。
- **外部包**放数据根下的 `craft/`：源码运行时是项目根目录（`workshop/craft/`），exe 是
  `%LOCALAPPDATA%\创作工坊\craft`。同名 `.md` **覆盖内置**；外部包没有的篇目照旧读内置，不是整库失效。
  外部包不入 git（`.gitignore` 里的 `/craft/`），也不进 exe。
- **加自己的篇目**两步：`CATALOG` 里加一条（`label` 必填，再给一个 `always` 或某个触发条件），放同名 `.md`。
- 默认预算 `DEFAULT_CRAFT_BUDGET = 10000`；选谁不选谁看 `CATALOG` 里的标记。

| 文件 | 篇目 | 什么时候带上 |
|---|---|---|
| `chapter-guide.md` | 章节写作指南 | 每一章 |
| `hook-techniques.md` | 悬念钩子十法 | 每一章 |
| `emotion-curve.md` | 情绪曲线 | 每一章 |
| `plot-structures.md` | 爽文情节结构 | 每一章 |
| `golden-opening.md` | 黄金开篇 | 第 1 章、每卷第 1 章 |
| `dialogue-writing.md` | 对话写作规范 | 本章指令里出现对话迹象时 |
| `continuity.md` | 连贯性机制 | 有「需承接」内容时 |
| `content-expansion.md` | 内容扩充技巧 | 目标字数写不够时（见下） |
| `character-building.md` | 人物塑造原则 | 本章有新人物登场时（见下） |
| `prompt-guide.md` | 提示词完善指南 | 助手备用，不给正文生成 |
| `quality-checklist.md` | 质量检查清单 | 审稿时 |
| `review-dimensions.md` | 章节审查维度 | 审稿时 |

`content-expansion` 与 `character-building` 目前**选不到**：`pick()` 还没读 `on_short` / `on_new_character`
这两个标记（那需要「字数缺口」「新人物」信号），这两篇只在 `available()` 里有份。接上信号时补这两条分支。

**方法**

- **做法**：`pick()` 只看 `CATALOG` 的触发标记、章号和本章指令里的字面线索（`narrative.focus` + `core_plot` + `one_line` 里出现「对话/说/问/谈/喊/骂/开口/回话」就算有对话），**不问模型**。 **为什么**：问模型「你需要什么技法」它一定说全都要。 **不这么做会怎样**：技法把输入预算吃掉，模型先看完几万字技法再看本章指令，写出来是一篇通顺、但没写这一章该发生的事的东西。
- **做法**：预算超了要点名。`render()` 只对「装不下」的篇目在段末列出名字，并说清是超预算。 **为什么**：「这一章不需要对话规范」和「技法库超预算没给」是两回事。 **不这么做会怎样**：混成一句「超预算」，作者会去调高上限——而调多高都改变不了「这一章没有对话」这个事实；反过来，少给一篇却不吭声，他会以为模型读过那篇。测试对最长的一次选择（4 篇 `always` + 黄金开篇 + 对话规范 + 承接）有断言：哪天加篇目把它顶出预算，测试会红。
- **做法**：外部包同名覆盖内置，读不到才回落内置；`CATALOG` 之外的文件不进库。 **为什么**：接别处的技法库只放文件、不改代码。 **不这么做会怎样**：一份文件缺失让整库失效，或者作者以为接上了、其实读的还是内置版，两种都只能靠翻日志才发现。
- **做法**：审稿只吃「质量检查清单」和「章节审查维度」两篇，生成用的技法一篇不给。 **为什么**：审稿拿着生成用的技法，会去评「开头够不够黄金」——那是生成阶段才该管的事。 **不这么做会怎样**：审查结论变成一堆生成阶段的要求，正文改不了，作者只能返工重写。
- **做法**：内置 12 篇本项目原创、随仓库与 exe 走；从别处收来的放外部 `craft/`，不入库、不进 exe。 **为什么**：这些文件名的早期版本放的是从 SkillHub 原样收录的外部技能包（作者「劳希」，页面声明「内容版权归原作者所有」，已从 git 排除并挪到外部位置）。 **不这么做会怎样**：带版权的内容跟着仓库与 exe 分发出去。**换一个 SkillHub 的 Skill 不解决版权**——页面底部那句「来源声明：……内容版权归原作者所有」是全站统一声明，对每个 Skill 都成立，换一个只是换了一个作者的版权。真要不带包袱只有两条路：自己写，或用已进入公有领域 / 明确开放许可的材料（中译本还要注意译者权利）。
- **做法**：内置篇目刻意压到每篇一两千字。 **为什么**：篇目够不够用，看的是能不能覆盖生成与审稿要管的事，不是字数。 **不这么做会怎样**：原来那套 83 KB 的包，光四篇 `always` 就超预算，一进去就把「这一章到底要写什么」挤没了。

**验证**

```bash
python tests/test_craft.py
```

查三件容易静默坏掉的事：

- 内置篇目缺文件——程序不报错，只是那篇技法静默不给，作者会以为模型读过。
- 外部覆盖没生效——放进去的包没被读到，还以为接上了；删掉之后要能退回内置。
- 预算不够——`always` 的篇目被静默砍掉，提示里只剩一句「超预算」；另外 `CATALOG` 之外的文件不许进库。

检验内置篇目时测试把数据根指到空目录，不然量的是你本机那个外部包，内置版坏了也看不出来。

## 写正文（起草一章）

**做什么**：把三层真源——设定集、本卷目录、本章创作任务指令——拼成一次调用，只写这一章。
写完落盘成 `.md`，并按当前指令做一遍机械自检；自检只查机器查得准的事，其余不假装查。

**用法**：

- 界面上选中某一章的指令，卡片按钮就直接写着这笔花费（`写这一章（约 ¥X）`）。点下去先弹确认框，
  说清目标字数、多少钱；这一章已经有正文时，框里多一句「会被覆盖」。
- 接口四步：`GET /api/works/{name}/creation/draft/{chapter_id}/plan`（免费，不调模型）、`POST` 同路径
  （会花钱，只出一章）、`GET`（读回并按当前指令重跑自检）、`PUT`（存作者手改过的正文）。
- 落盘是两处：正文写成 `90-draft/<chapter_id>.md`（普通 Markdown，作者能拿去任何地方读），
  元数据写成同名 `.json` 侧车——模型、用量、`finish_reason`、是否截断、自检结论都在里面。
- 手改直接在那个大文本框里改，`PUT` 存回；要存的是空文本、而磁盘上这一章已经有内容，写入会被拒绝，
  免得把正文清空。

**方法**

- **做法**：三层真源按 `写前必读 → 设定集 → 本卷目录 → 本章指令 → 技法参考 → 参照素材 → 字数` 拼成一条 user 消息，system 里只放硬约束。 **为什么**：写前必读是锚点，要压在所有内容之上；测试断言顺序必须是「设定集 → 本卷 → 本章指令」。 **不这么做会怎样**：模型先读完几千字设定集才看到本章要写什么，锚点就成了「事后补充」而不是「动笔前钉住」，写出来的东西对不上这一章。
- **做法**：一次只出一章，跑完就停，不自动串章。 **为什么**：这是作者自己的书，一次吐十章，他改起来等于重写；第一章就不满意的话，后面九章的钱和读的时间都白花。 **不这么做会怎样**：作者的否决权被一个批量按钮换走——省下几次点击，换来的是没法在第一章叫停。
- **做法**：字数去掉所有空白按字符数，区间取自本章指令的 `word_target`（默认 `[2800, 4000]`）；不到下限一半（`SHORT_RATIO = 0.5`）阻断，偏短或超出上限都提示，**不给宽容带**。 **为什么**：宽容带会造成「统计说不在区间内、却一条提示都没有」的假绿灯——实测真写第一章时 4784 字对 2800–4000 的目标静默通过。 **不这么做会怎样**：作者照着统计以为没事，而假绿灯比不查更坏。
- **做法**：截断查两路——`finish_reason` 是 `length` / `max_tokens` 时直接标截断，另外独立看正文末尾是不是句末标点。 **为什么**：实测这家 API 的 `finish_reason` 返回 `None`，光靠它等于没查；末尾断没断是独立于供应商的信号。 **不这么做会怎样**：作者以为模型写完了，其实后面少了半章，而它读起来像正常结尾。
- **做法**：提示词要求「只输出正文」，但回来仍然洗一遍壳：markdown 标题、`第 X 章` 行、``` 围栏、整段引号。 **为什么**：它总会加，要求归要求，回来还是要洗。 **不这么做会怎样**：正文文件里混进「第 1 章 数值」这行，后面所有字数统计和拼接都跟着脏（正文中间本来就有的「第 3 章」字样不能误删，测试盯着这一条）。
- **做法**：先出一份**免费**计划（token、费用、会喂进去什么），把技法也算进输入估算；没填单价就不给数字；缺指令、或指令与设定集有阻断时 `ready=False`，按钮不可点。 **为什么**：作者是照着这个数决定要不要点下去的，技法一篇几千字，不算进去低估起来是成倍的。 **不这么做会怎样**：显示的费用明显低于真实，作者在不知情的情况下花掉多一倍的钱。

**验证**

```bash
python tests/test_draft.py
```

不联网、不花钱，查机器查得准的几件事：

- 洗壳：8 个用例——markdown 标题、`第 X 章`、``` 围栏、整段引号都洗掉，本来就干净的保持不变；
  正文中间的「第 3 章」字样不被误删。
- 字数：空白不计入；区间内、过半偏短、刚过上限、空正文分别是什么结论。
- 截断：末尾断开要报，末尾是 `。！？…”` 不算；这条不依赖 `finish_reason`。
- 禁令字面命中是阻断；指令里写了要出场却没出现的人要被点名。
- 没指令、或指令有阻断时 `ready=False`，并说清原因。
- 计划：三层都算进输入、目标字数取到、费用与输出 token 按上限估、单价说明写了时段。
- 提示词：三层都在、顺序是设定集 → 本卷 → 本章指令，system 里带着那几条硬约束。
- 落盘：`.md` 与 `.json` 侧车都能读回，没写过的章节返回 `exists=False` 而不是报错。

钩子够不够、情节顺序对不对、伏笔回收得漂不漂亮——机器查不了，硬查只会给假绿灯，所以不查。

## 作品录入与切分

**纯脚本，不调模型。** 这是唯一一个完全独立于外部服务的模块，也是拿真实作品跑通全链路的前置条件。

```
python ingest_cli.py --demo                                    # 合成文件演示
python ingest_cli.py --file 关山灯.txt --preview                # 只预览，不落盘
python ingest_cli.py --file 关山灯.txt --out workspaces/关山灯/00-ingest
python ingest_cli.py --file 关山灯.txt --out ... --strip-repeated   # 顺便删页眉
```

### 切分是三步，不是一步

```
① 候选识别   找出所有命中模板的行，此时不切分
② 序列校验   章号必须单调递增、步长符合预期
③ 断点修复   缺口区间用宽松模板重扫
```

**序列校验是关键。** 没有它，你无法区分「第 6 章标题格式写错了」和「这本书本来只有 5 章」——序列的连续性是最强的信号。

宽松模板**只在缺口里用**。全文用宽松模板会把正文里的「三、他抬起头」也当成标题。

### 排除三类干扰

| 干扰 | 判定方式 |
|---|---|
| 目录页 | 连续标题行之间**只允许有空行**；出现任何别的文字（卷标题、正文）即终止 |
| 正文引用 | 标题行里带引号（`「」『』""`）即排除 |
| 正文行 | 严格模板里**不包含**「数字+分隔符」和「任意短括号行」——这两类在正文里满篇都是 |

### 三条绝不妥协的规则

**① 一条都不丢。** 遇到重号，**保留并加字母后缀**（`v001-c0376b`），记异常让人确认——
绝不丢弃。丢弃会让那一章的正文被静默并进上一章，看起来只是少一章，实际是内容被悄悄拼接。

**② 编号重启不是重号。** 标题行或紧邻上一行出现「番外 / 第二部 / 楔子」等标记时，
章号回落到小数字会被判定为**新分段**，开启新的段号。真实作品里番外篇常常重新从第一章编号。

**③ 异常判据只用相邻项，不用历史最大值。** 一个错字（如「第9229章」实为「第922章」）
若与历史最大值比较，会把此后每一章都判成乱序，凭空造出上百条告警。

### 两个探针（只在真实作品上才显得重要）

| 探针 | 作用 |
|---|---|
| **模板命中分布** | 主模板 1056 次、另两个模板各 17 和 20 次——占比过低的几乎一定是误报，一眼看得出 |
| **格式变体探针** | 捞出「像章节标题但没命中任何模板」的行。真实作品里番外章节写成「番外XXX」，严格模板全落空，这些内容会被并进上一章，只看总数发现不了 |

### 容错修复

宽松模板里有专门一条处理**标题里的错字或乱码**（如「第缌妣380章」「第424钌章」）。
这类章节因为标题不匹配会整体丢失。宽容模板只在缺口区间使用、且结果必须落在缺口章号上，
所以误报风险很低。

### 清洗铁律

| 做 | 不做 |
|---|---|
| 去 BOM、行尾空白、连续空行归并 | **不删标题行**（下游钩子比对要用） |
| 每次删除写日志（含章节归属） | **不做标点规范化**（标点是风格指纹） |
| 清洗前后各存一份 | 页眉页脚**默认只报告不删**（要显式开 `--strip-repeated`） |

### 完整性核验：重建校验

```
把「章前区段 + 所有章节的原始切片」按原顺序拼回去，必须与原文件逐字一致
```

**这比对比字数强得多**——它连切片偏移算错都能抓出来。再加减一个字数对账（Σ章节 + 章前 = 源码字数，偏差 >0.5% 阻断）和逐章切片校验。

门禁不通过就不该进入标注阶段。

### 产出

```
00-ingest/
├── chapters/         清洗后的章节（带 front-matter，标注模块直接吃）
├── raw-chapters/     清洗前原文，用于对照
├── manifest.json     清单：卷结构、逐章字数/哈希/字节偏移、异常、核验结果
├── cleaning-log.jsonl  每次删除的审计日志
└── _review/          异常复核队列
```

### 验证

```bash
python tests/test_ingest.py
```

覆盖：中文数字转换、编码探测（含 GB18030）、**目录页不吞第一章**（真实事故的回归）、
缺口修复、重号与正文引用排除、清洗的保守性（标题行保留 / 标点不动）、
页眉只报不删、重建校验、落盘回读。

## 单章标注

调用基准定好之后，标注模块只是换提示词与调度方式。目前完成的是**单章往返链路**，
不含批量调度——链路先跑通，批量只是加并发。

```
python annotate_cli.py --demo                  # 演示：本地模拟服务，不花钱
python annotate_cli.py --chapter-file <路径> --script-only    # 只算脚本轨，零成本
python annotate_cli.py --chapter-file <路径> --provider deepseek   # 真实标注一章
```

### 标注结果 = 脚本轨 + 模型轨

| 轨 | 内容 | 成本 |
|---|---|---|
| **脚本轨** | 字数、段落、平均段长、对话占比、人称检测、风格违规 | **零** |
| **模型轨** | 视角、场景切换、时间跨度、钩子、情绪、冲突、信息释放、主线推进、支线、爽点、伏笔、动机强度 | 一次调用 |

这个划分直接决定成本结构：**风格违规检测（破折号、句式、人称）全部由正则完成，不花一分钱**，
不该交给模型。

### 消息结构（缓存的前提）

```
messages[0] system —— 固定前缀：系统提示 + 原语 schema + 约束 + 作品动机设定
messages[1] user   —— 变量尾巴：上一章摘要 + 本章正文
```

**顺序不可调换。** 缓存按前缀匹配，把变量插在固定内容之前会让缓存全部失效。
`prefix_hash` 会写进标注产物的来源信息，便于日后确认哪些标注用的是同一套前缀。

### core_motive 为空怎么办（不要让它变成假数据）

`core_motive` 是 P21「主角核心动机呈现强度」的**度量对象定义**，写在固定前缀里。

留空时**流程照样能跑**（CLI 只警告，不阻断），但有个陷阱：模型会自己编一个动机来打分。
实测它给了 3 和 4——而「猜出来的分数」和「诚实的空值」在数据集里**长得一模一样**，
事后根本分不出来。猜的那个更糟。

所以前缀里加了一条显式指示：

> 作品未定义主角核心动机。`motive_strength` 一律填 `null`，不要自行猜测任何动机来打分。

并且声明它**优先级高于**「本章没有出现的内容，强度类字段填 1」的通用约束——
否则两条规则打架，填 1 会被误读成「动机存在但很弱」（其实是没有度量对象）。

想补就在 `workspaces/{作品}/work.yaml` 里填。**填了之后旧标注的 P21 列与新标注不可比**
（工作配置哈希变了，会体现在 provenance 里），建议重跑受影响的章节。

### 三条纪律

| 纪律 | 落实方式 |
|---|---|
| **校验失败绝不静默填默认值** | 缺失/非法字段值保持 `null` 并记入 `validation_issues`，转 `needs_review` |
| **每章一个独立文件** | 幂等键是原文 sha256；改一个字才重跑一章 |
| **落盘前统一脱敏** | 上游错误体可能夹带密钥，而错误体要写进记录 |

### 复核分级

模型会额外返回自评置信度：

| 自评 | 复核动作 |
|---|---|
| 高 | `auto_accept` |
| 中 | `spot_check` |
| 低 | `must_review` |

**只强制复核低置信度章节**，人工工作量可能降到原来的三分之一。

## 批量标注调度

单章链路跑通之后，批量不是重写，而是加四件事：筛选、估算、控并发、能续跑。

```
python batch_cli.py --work 示例作品                      # 只出计划，不调模型
python batch_cli.py --work 示例作品 --run --limit 20 --yes  # 试跑 20 章
python batch_cli.py --work 示例作品 --run --yes            # 全量
python batch_cli.py --demo --run                                # 本地模拟跑一遍，不花钱
python batch_cli.py --work 示例作品 --status               # 看最近一次跑到哪
```

### 并发与台账的顺序依赖（一个绕不开的取舍）

伏笔台账和「上一章摘要」都要求**第 i-1 章的结果在第 i 章发起调用之前就确定**：

- 章 i 的提示词里带着未回收伏笔清单，它必须包含章 i-1 刚埋下的编号，
  否则章 i 只能把同一个伏笔再登记一次；
- 章 i 的上一章摘要来自章 i-1 的标注结果。

所以这两件事天然要求串行。实测（合成作品 8 章）：

| 并发 | 伏笔台账结果 |
|---|---|
| **1（默认）** | 1 条伏笔，事件链 `埋设 → 推进 ×7` |
| 4 | **4 条**伏笔——同一条线索被重复登记了 4 次 |

处理方式不是偷偷并发，而是把选择权显式交出去：默认并发 1；
传 `--concurrency N` 时计划里会明确写出「台账上下文滞后最多 N-1 章」。

**这条取舍被写成了断言**（`tests/test_batch.py`）：并发 4 下伏笔数必须大于 1，
用来保证这个代价始终可见，不会哪天被悄悄改掉。

### 运行记录：不能只报「失败 20」

只给一个失败数量等于让人猜。所以：

| 层次 | 内容 |
|---|---|
| 错误按类别汇总 | `auth_failed` 20 次 —— 每一类都带**下一步怎么办**（`errors._HINTS` 表） |
| 失败章节列表 | 每章的最后一次报错原文（界面里可直接看，不用去翻文件） |
| 运行记录文件 | 界面给出完整路径，摘要之外还能看到全文 |

加这个是因为真实踩到：密钥失效时界面只说「失败 20」，原因躺在状态文件里没人看。

### 配置类错误立刻停

`auth_failed` / `endpoint_not_found` / `model_not_found` 这三类是**配置问题，不是抖动**，
重试再多次也不会好。撞上就中止并说明原因。

不这么做的话：实测密钥失效时，任务拿同一个 401 把 20 章各重试 3 次、白跑 8 秒；
跑 933 章要白等十几分钟，而且日志里堆满同一个错误，真正的原因反而被埋掉。

### 三条纪律

| 纪律 | 为什么 |
|---|---|
| **失败不落盘** | 失败的章一旦落盘，幂等判定会认为「已有标注」而永久跳过它。一次网络抖动就变成一章永久缺数据，且毫无提示 |
| **超预算中止** | 估算只是估算，真正拦闸的是实测 usage 累计。上限到了就停，剩下的重跑时接着跑 |
| **成本要能追到每一项** | 章数、系数、单价全部列出。没有单价就明说算不出，绝不给假数字 |

### 估算里哪些是实测、哪些是假设

| 项 | 来源 |
|---|---|
| 输入侧（固定部分 + 正文） | **批量实测拟合**：`prompt ≈ 940 + 正文含空白字符数 × 0.6754`，残差 ±100 token |
| 正文长度 | 读章节文件实测（**含空白与缩进**，比 manifest 的非空白字数多约 24%） |
| 输出 token | **批量实测** 263/章；没有实测时才退回假设值 300 |
| 单章耗时 | **批量实测** 1.52 秒 |
| 单价 | 你填的；没填就不显示费用 |
| 上一章摘要 + 伏笔清单 | 仅在**没有**批量实测时作为假设值叠加（实测截距已包含它） |

上面这些实测值存在 `providers.yaml` 的 `measured_batch` 里，跑一次真实标注就能刷新。

#### ⚠️ 为什么不能直接用探测的系数

P5 探测给出的系数是 **0.968 tokens/字**，而真实散文只有 **0.675**——差 1.43 倍。

原因是探测用的是**合成文本**（千字文片段反复重复），没有标点、换行、缩进、数字；
而真实源文本每段带 4 空格缩进，空白占 19%，而空白也要计入 token。

`probe-recipe-v2` 已把合成文本改成「像真实散文」（空白 22% vs 真实 19%）。
但**最可信的校准来源永远是跑一次真实标注**——20 章的样本就够拟合出靠谱的系数。

## 伏笔台账（跨章状态的唯一来源）

伏笔天然跨章，而逐章标注每次只看一章。常见错误做法是「把上下文扩到 10 章」——
那会立刻撞上 token 预算和长上下文退化（300 万字 ≈ 上百万 token）。

**正确做法是把跨章状态外化成文件**：每章只读台账、只改台账，从不把历史原文塞进上下文。
状态因此从「上下文里的信息」变成「文件里的状态」，这才能扩展到上千章。

### 编号由台账分配，不由模型

实测中让模型自己编编号，同一章跑三次分别给出 `F1`~`F4`、`F-01`~`F-04`、以及留空。
跨章必然对不上，台账就废了。

所以约定：

| 动作 | 模型做什么 | 台账做什么 |
|---|---|---|
| 埋设 | 编号**留空** | 分配 `F-00X` 并**写回标注结果** |
| 推进 / 回收 | 引用清单里的编号 | 校验存在性，追加事件，更新最后推进章 |

**写回很关键**：落盘的标注文件必须带台账的规范编号，否则标注文件自身不自洽。

### 三种「没按预期发生」都要留痕

| 情况 | 处理 |
|---|---|
| 引用了不存在的编号 | 记异常，并按「埋设」重新登记——**宁可多记一条，也不丢信息** |
| 未填编号就推进/回收 | 同上 |
| 对已回收的伏笔再做动作 | 记异常，忽略该动作，状态不被改回 |

### 疑似断点

长期未推进的未回收伏笔（默认 30 章）会被识别为**疑似断点**——这是体检报告里最有价值的一节。

### 台账文件

```
workspaces/{作品}/20-kb/k2-material/foreshadow-ledger.json
```

保存顺序：**标注成功落盘之后才保存台账**。反过来的话，一次落盘失败就会留下
「编号已分配但标注不存在」的幽灵条目。

### 验证

```bash
python tests/test_ledger.py
```

含一条缓存相关的关键断言：**未回收清单必须进变量部分，不能污染固定前缀**——
它每章都在变，放进前缀会让 prompt 缓存全部失效，直接抬高整本书的输入成本。

## 标注台：逐章人工复核

**做什么**：模型先把全本标一遍，人只处理「需要看一眼」的那部分。左栏是章节与状态（按卷分组、带色标），中栏是正文（模型判的爽点候选段落会高亮），右栏是模型轨字段面板。保存写回 `workspaces/{作品}/10-annotations/{chapter_id}.json`，改的是字段和状态，不动正文。

**用法**：作品页点「标注台」，或直接开 `#/work/{作品名}/annotator`。左栏一次拉全、不分页，未标注 / 已标注 / 待复核三色区分，点章跳转，`J`/`K` 翻上一章下一章。右栏控件默认是禁用的，先点「编辑字段」才能改——省得误点改掉模型输出；「保存修改」落盘，「确认本章」只改状态。`Space` 保存并进下一章，`Ctrl+S` 保存，`?` 出快捷键表。

中栏正文里的高亮来自 `fields.payoffs` 的「锚点」：锚点写错了就会高亮到别的段落，这是判断模型有没有读准原文最快的办法。标注台本身不做筛选；要按状态筛整本书，用作品页的「标注总览」（`GET /api/works/{作品名}/annotations?only=review|ok|all`）。

接口：

```
GET /api/works/{name}/annotator/fields                    # 右栏字段定义（只给模型轨）
GET /api/works/{name}/annotator/chapters                  # 左栏章节列表 + 状态
GET /api/works/{name}/annotator/chapters/{chapter_id}     # 中栏正文 + 当前字段，不存在给 404
PUT /api/works/{name}/annotator/chapters/{chapter_id}     # 保存人工修正
```

作品没有章节数据时「章节列表」给 400；章节还没有标注记录时 `PUT` 也给 400——标注台是修正，不是 create。

**方法**

- **做法**：落盘的 `status` 只有两个值——`ok` / `needs_review`，但凡出现校验失败、缺字段、自评置信度为「低」、模型自己列了存疑字段、或伏笔台账报异常，一律转 `needs_review`。 **为什么**：人是按队列干活的，不是按书干活的；没有队列就得逐章重看整本。 **不这么做会怎样**：上千章的作品里，模型 90% 的输出是对的，但没人知道是哪 10% 不对，复核这件事会在前十章之后被放弃。

- **做法**：复核分级写在 `annotate.py` 的 `_CONFIDENCE_ACTION`：自评「高」→ `auto_accept`，「中」→ `spot_check`，「低」→ `must_review`，没返回自评就按 `spot_check`（同时往 `issues` 里塞一条「模型未返回自评置信度」）。 **为什么**：`review_action` 回答「人该看哪几章」，`status` 回答「这章现在能不能当正常数据用」，两者不是一回事——自评「中」且无异常时 `status` 仍是 `ok`，只是建议抽查。 **不这么做会怎样**：把「建议抽查」写成「必须复核」，队列会重新变成全量，等于没有分级。`primitives.yaml` 里的 `review_policy` 是同一份约定的说明，真正生效的是代码里那张表。

- **做法**：人工修正走浅 merge——只覆盖提交上来的、且**记录里已经存在**的键；没定义的字段直接忽略，没有标注记录的章节直接拒（400）。 **为什么**：字段集由 `primitives.yaml` 固定，体检、对比、知识库都按同一套 key 聚合。 **不这么做会怎样**：标注台某天临时加一个字段，跨作品聚合就出现「有的作品有这列、有的没有」，对比表从此没法看。

- **做法**：人改字段后记录级留痕——`provenance.reviewed_at`、`provenance.reviewed_by = "ui-annotator"`，`reason` 写进 `issues`（形如「人工修正：……」），并且状态自动扭回 `needs_review`。字段值本身**没有**逐字段的来源标记，人改过的和模型输出的是同一个 `fields` 字典。 **为什么**：记的是「为什么改」，而不是给每个值再挂一层出处——标注台是高频操作，多一层结构就多一次填表。 **不这么做会怎样**：改完就没了痕迹，事后分不清「这个分数是模型的还是人拍的」；要靠 diff 找旧值，只能去 `10-annotations/_archive/` 翻批量重跑时归档的那一版（人工保存是原地更新，不归档）。

- **做法**：批量标注跳过已标注章节时看两件事——原文 `sha256` 一致，且上次不是失败或空产出（`_needs_rerun`）。人工修正既不改正文也不动 `source.sha256`，所以再点一次批量标注时这章会被算作已完成，直接跳过。 **为什么**：幂等判定的语义是「这章的正文有没有变过」，不是「文件在不在」——人工改字段改的是判断，正文没变，这章就没必要重标。 **不这么做会怎样**：一次批量就把整本的人工复核冲掉，没人敢再点那个按钮。真需要重跑时（改了提示词或作品配置）得显式带上批量的 `force`；重写前旧文件会先挪进 `10-annotations/_archive/`（带时间戳），不至于丢。

- **做法**：`annotator/fields` 只返回模型轨字段，脚本轨（字数、段落、对话占比、人称检测、风格违规）不在右栏里，它的问题以 `issues` 文本显示在章头。 **为什么**：正则算出来的东西人复核没有意义，值得人看的是那一段正文本身。 **不这么做会怎样**：右栏塞进十几个确定性的数字，真正要判断的评分字段被挤下去，复核反而更慢。

**验证**

```bash
python tests/test_annotator.py
```

覆盖了：`fields` 返回模型轨字段（含评分字段与 `payoffs` / `foreshadows` 这类对象列表）与 `field_order`；`chapters` 把全部章节读出来，未标注章状态为空；单章明细带正文、字段、自评与前后章导航，不存在的章给 404；保存修正的几条纪律——改字段自动转 `needs_review` 并落盘、显式 `ok` 生效、未定义字段不落盘、未标注章拒绝保存（400）、只改提交的字段其他保留；未知作品给 400 而不是 500。

## 知识库

**做什么**：把已经有的标注与实体统计换个角度排好，产出三层——K1 实体卡片、K2 四类台账（人物 / 支线 / 时间线 / 伏笔）、K3 作品指纹。全部是本地脚本聚合，不调模型，零成本。它不产生新信息，只让已有信息能拿来用。

**用法**：作品页点「知识库」，或直接开 `#/work/{作品名}/kb`。没构建过就一个「构建知识库」按钮；构建过则展示三层内容与「重新构建」。什么时候都能建：K2 人物出场只要有实体统计和正文就能算，不需要标注；改过标注之后要重新构建一次才会反映到 KB。

接口：

```
GET  /api/works/{name}/kb          # 读最近一次（读的是 20-kb/index.json）
POST /api/works/{name}/kb/build    # 构建，纯脚本
```

没构建过时 `GET` 返回 `{"exists": false}`——这是正常状态，不是错误。作品还没有章节数据时构建返回 400 并说明原因。

产物在 `workspaces/{作品}/20-kb/`：

```
20-kb/
  index.json               # 三层全量，GET /kb 读的就是它
  k1-entities.json         # K1，实体统计 50-entities/latest.json 的副本
  k2-material.json         # K2 三类台账（人物 / 支线 / 时间线）
  k3-fingerprint.json      # K3 作品指纹，体裁与跨作品对比也读这个文件
  latest.md                # 给人看的一页摘要（人物出场表 + 指纹条目）
  k2-material/             # 注意与上面的 k2-material.json 同名不同物
    foreshadow-ledger.json # 伏笔台账，由标注与批量单独维护，KB 不复制
```

**方法**

- **做法**：整个构建过程只做聚合——正则、计数、序列分析，一次模型调用都没有。 **为什么**：知识库的价值是「把已有数据换个角度排好」，不是产出新判断；K2 人物出场是字符串匹配，K3 指纹是已有标注的均值和分布。 **不这么做会怎样**：为了 KB 再把全本读一遍，一本三百万字的书就是再烧一遍全本的钱，而换来的还是同一批数字。

- **做法**：K1 直接把 `50-entities/latest.json` 的 `merged` 复制过来，不重算人物、势力、能力、地点、关系；没有这份文件时返回 `available: false` 加一句说明，界面显示「无实体统计」而不是空白。 **为什么**：实体识别的口径只能有一处，重算就会漂移。 **不这么做会怎样**：知识库里的人物和作品页「世界观与人物」里的人物对不上——两套名字、两套别名，人物卡片当场失去可信度。

- **做法**：K2 人物台账拿 K1 的人物名**和别名**去正文做包含匹配，得到出场章列表、首次/最后出场、覆盖率；名字短于 2 字的跳过，正文一次都没命中的条目直接不列，`note` 里写明这是纯字符串匹配、会有误命中。 **为什么**：不把别名算进去，「出场章数」量的是名字的拼写而不是人。 **不这么做会怎样**：用户看到「某人物 164 章」时以为是精确统计，其实里面混着短名字的误命中；把噪声写在 note 里，这些数字才能被当参考而不是结论。

- **做法**：另两类台账也一样——支线只给「在场区间」和「变化点」，不给支线名（标注里只有 `subplot_count`，没有名字也没有编号），伏笔一栏只留一句指向 `k2-material/foreshadow-ledger.json` 的说明，不复制台账内容。 **为什么**：「数据不足」是可以写出来的结论，编一个名字出来不是；伏笔编号由台账分配（见伏笔台账那一节），复制一份必然分叉。 **不这么做会怎样**：凑出来的支线名跨章对不上、同一批伏笔在 KB 和台账里两个编号，两份看着完整的台账都没法用，比空白更坏。

- **做法**：K3 有样本门槛和置信度分级——标注不足 5 章直接 `available: false` 并说明「没有统计意义」；≥50 章算「高」，20–49 章算「中」，不足 20 章算「低」；每一条都带 `rule`、`sample`、`confidence`。 **为什么**：均值这种统计量在小样本上什么都能得出。 **不这么做会怎样**：3 章的均值被当成全书指纹，后面所有基于指纹的对比（体裁、跨作品）都建在噪声上。

- **做法**：K3 除了均值和分布，还专门输出两类**指路**条目——连续 3 章以上量表值不变的走平区段（情绪值、冲突等级），以及钩子强度 ≤ 2 的章节清单。 **为什么**：数字不构成结论，它的用处是告诉你「哪里该去看原文」。 **不这么做会怎样**：报告变成「模型说你这章平淡」，作者既没法验证也无从下手。

**验证**

```bash
python tests/test_kb.py
```

覆盖了：没构建过时 `GET /kb` 返回 `exists: false`（不是错误）；构建后返回 K1/K2/K3 三层；K2 人物台账有计数、时间线有跨度分布、支线有在场区间，且支线那一栏显式说明数据不足、不编造；K3 在标注足够时可用且每条带样本量与置信度；四个产物文件确实落在 `20-kb/` 下；构建后能读回；只有 3 章标注时 K3 标记为不可用并说明原因；未知作品构建给 400 而不是 500。

## 实体统计

**做什么**：从**正文**里逐块抽取人物、势力、能力、地点、人物关系，归并成五张表。
原料是正文而不是梗概——梗概一句话 60 字，装不下人物关系的细节。
三条纪律：只抽原文里出现的（宁可少，不能编）、每个人物给首次出现章号、失败的块显式标出来。

**用法**

```bash
python entities_cli.py --work 示例作品                       # 只看计划，不调模型
python entities_cli.py --work 示例作品 --run --yes            # 真跑
python entities_cli.py --work 示例作品 --run --yes --limit 3  # 本次只跑 3 块，再跑一次接着跑
python entities_cli.py --work 示例作品 --status               # 打印 50-entities/latest.md
python entities_cli.py --demo --run                           # 本地模拟，不花钱
```

参数（以 argparse 为准）：

- `--work` 作品名，`--config` 配置文件（默认 `providers.yaml`）
- `--block-size` 每块几章，默认 50
- `--provider` / `--model`：不填则取 `providers.yaml` 里 `entity_extraction` 的任务绑定
- `--max-tokens` 单块输出预算起点；不填取模型声明的 `max_output`，封顶 32000
- `--limit` 本次最多跑几块；没轮到的标成「还没跑」
- `--ingest-dir` 默认 `workspaces/{作品}/00-ingest`，`--out-dir` 默认 `workspaces/{作品}/50-entities`
- `--run` 才真跑，`--yes` 跳过确认，`--status` 只打印上次结果，`--demo` 用本地模拟，`--timeout`

产物在 `workspaces/{作品}/50-entities/`：`entities-{时间戳}.json` 与 `.md`、`latest.json` / `latest.md`（界面读它）、`_state.json`（断点记录）。
别名表是可选的，放在作品根目录 `workspaces/{作品}/aliases.yaml`。

界面：作品页点「生成实体统计」，先给计划（几块、正文多少字、预估 token 与费用，免费），确认框里写清这次跑几块。
生成后进 `#/work/{作品}/entities`（导航「世界观与人物」）看五张表和三类块；
有没跑完的块时页面上有「继续生成（还有 N 块）」和「本次只跑 N 块」输入框。

接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/works/{name}/entities/plan` | 计划，免费；`block_size`（默认 50，限 5～200）、`provider`、`model` |
| POST | `/api/works/{name}/entities/start` | 开始或接着跑；`limit` 限定本次跑几块（1～500） |
| POST | `/api/works/{name}/entities/stop` | 请求停止，当前块跑完即停，已完成的块保留 |
| GET | `/api/works/{name}/entities/status` | 在跑吗、进度、有没有结果、还剩几块 |
| GET | `/api/works/{name}/entities` | 最近一次产物；没生成过时 200 + `exists: false` |

最后那个不用 404：它是这个接口的正常状态之一，用 404 浏览器会在控制台留一条假错误，而假错误会训练人忽略真错误。

**方法**

- **做法**：每 `block_size` 章一块（默认 50），逐块调用；块的文本由章节文件剥掉 front-matter 后拼成，每章带上 `【第N章 标题】`。
  **为什么**：一次把几百章正文塞进一次调用，长输入里的细节会被忽略，而且任何一处失败就得整本重跑。
  **不这么做会怎样**：细节丢一半，还得付第二遍钱。
- **做法**：只跑一部分（`--limit`、界面的「本次只跑 N 块」）或中途点「停止」时，没轮到的块标 `pending` 落盘，下次接着跑；已完成的块直接复用缓存。
  **为什么**：一本 545 章按 50 章一块是 11 块，一口气跑不完是常态。进度上报只在真的要发调用时才打——跳过的块也报一遍，命令行会打印「抽取第 2 章」却没扣费，看起来像跑过了一样。
  **不这么做会怎样**：长任务只能一口气跑完，中途停下前功尽弃，已花的钱白花。
- **做法**：撞上 `max_tokens` 截断先翻倍输出预算重试；加到上限（32000）还是断，就从截断处抢救出写完整的部分，标 `salvaged` 并附一句说明。
  **为什么**：实测一部 545 章、每块 50 章的连载，写死 4000 时 11 块里有 9 块被截断。旧版还照原样重试三次——每次都断在同一处，白烧 448 万 token，最后报出来的原因却是「返回内容不是 JSON」，与真实病根毫无关系。
  **不这么做会怎样**：钱花了、整块数据丢掉、错误信息还把人指错方向。
- **做法**：「失败」「还没跑」「被截断只抢救出部分」是三个不同的标记（`error` / `pending` / `salvaged`），产物、Markdown 顶部的提醒、界面上的 chip 与详情列表都分开写。
  **为什么**：空数组加上没有错误，会被读成「这一段真的没有实体」——把没做的事说成做完了，比报错更糟。
  **不这么做会怎样**：读的人以为这本书前 50 章一个角色都没出场。
- **做法**：归并时同名只留一张卡、`first_chapter` 取最早；匹配规则只做到「完全一致」和「互为子串」两级，不同叫法交给 `aliases.yaml`（别名 → 正名），并且正名要落到每一张表：人物关系表的 from/to、势力成员、能力持有者。
  **为什么**：实测一部 545 章里，张老师 / 张老鳖 / 张教授是同一个人（正文第 1、28、303 章都写明），却被抽成三张卡，还在关系表、势力成员、能力持有者里各算一份。
  **不这么做会怎样**：人物数量虚高，关系表两边对不上。规则归并认不出改称呼、本名、化名，剩下的留给人工核对——假装合并成功比不合并更糟。
- **做法**：提示词里写死「只整理原文明确出现的东西」「原文没给名字就用原文的称呼」「relations 只记双向都成立的关系」；部分中转站不认 `response_format=json_object`，第一次撞上 `BAD_REQUEST` 就记住，本块后续重试降级成提示词约束 + 解析。
  **为什么**：模型自己补全设定是这一步最容易出的错，而错误的名字会一路流进关系表和后继模块。
  **不这么做会怎样**：拿到一份看着完整、却没有一条能在原文里找到的设定表。

**验证**

```bash
python tests/test_entities.py
```

七个用例，每个都对应一次真实失败：截断的 JSON 只抢救出写完整的条目（没写完的那条不要，没写到的字段不凭空出现）；
截断时预算从 8000 翻到 16000 后拿到完整结果；预算加到顶仍截断时保住截断前的人物并标 `salvaged`；
普通文字不被误判成截断、预算也不无谓翻倍；`limit=1` 时另两块标 `pending`，第二次只跑缺的两块；
中途停止保留已完成的块并记下「是被停下来的」；别名归并落到人物卡、势力成员、能力持有者与关系表每一张，
不给别名表时行为不变（不猜、不并）。

## 大纲

**做什么**：把逐章梗概逐层归约成一份能读的大纲——每 50 章一块先归约成一段段梗概，再用各段梗概归约出全书大纲
（一句话、开局设定、分段结构、线索、关键转折、结局、模型自评置信度）。
原料是标注时顺带产出的 `chapter_summary`（P22），不额外花钱，所以**大纲的前置条件是有标注**。
没有标注时它直接说缺原料，不生成一份凭空的大纲。

**用法**

```bash
python outline_cli.py --work 示例作品                  # 只看计划，不调模型
python outline_cli.py --work 示例作品 --run --yes       # 真跑
python outline_cli.py --work 示例作品 --status          # 打印 40-outline/latest.md
python outline_cli.py --demo --run                      # 本地模拟，不花钱
```

参数（以 argparse 为准）：

- `--work` 作品名，`--config` 配置文件（默认 `providers.yaml`），`--primitives`
- `--block-size` 每块几章，默认 50
- `--annotations-dir` 默认 `workspaces/{作品}/10-annotations`，`--ingest-dir` 默认 `00-ingest`
- `--out-dir` 默认 `workspaces/{作品}/40-outline`
- `--provider` / `--model`：不填则取 `providers.yaml` 里 `volume_review` 的任务绑定
- `--max-tokens` 单次输出上限；不填按模型声明的 `max_output` 定，撞上截断会自动翻倍重试
- `--run` 才真跑，`--yes` 跳过确认，`--status` 只打印上次结果，`--demo` 补演示梗概并走本地模拟，`--timeout`

产物在 `workspaces/{作品}/40-outline/`：`outline-{时间戳}.json` 与 `.md`、`latest.json` / `latest.md`（界面读它）、`_state.json`（各段梗概的断点）。
JSON 里除了大纲还带 `plan`：这次用了哪个模型、几块、估了多少费用。

界面：作品页点「生成大纲」，确认框里列出服务商 / 模型、归约块数（`blocks + 1`）、覆盖多少章梗概（缺多少章）、预估费用；
没就绪时这个框直接把计划里的警告抬出来（通常是「先跑标注」）。
生成后进 `#/work/{作品}/outline` 看一句话、开局设定、分段结构、线索、关键转折、结局、置信度，以及可展开的逐段梗概。

接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/works/{name}/outline/plan` | 计划，免费；`block_size`（默认 50，限 5～200）、`provider`、`model` |
| POST | `/api/works/{name}/outline/start` | 开始一次生成；`block_size`、`model` |
| GET | `/api/works/{name}/outline/status` | 在跑吗、跑到第几块、有没有结果 |
| GET | `/api/works/{name}/outline` | 最近一次大纲；没生成过时 200 + `exists: false` |

**方法**

- **做法**：`build_outline_plan` 按章序收梗概、分块，只把**有**梗概的章切成块；缺梗概的章不静默跳过，而是计数、按原因分类、写进 `warnings`，`ready` 标成「一章不缺且有块」。
  **为什么**：大纲的唯一原料就是 `chapter_summary`，没有原料就该停下；而且「计划」免费、「执行」要用户点，成本按块数一眼可见。
  **不这么做会怎样**：生成一份结构完整、内容全靠猜的大纲，读的人会拿它当依据——那正是这个项目一直在防的静默失效。
- **做法**：分层归约——逐章梗概每 50 章一块归约成段梗概，再拿所有段梗概做一次全书归约；每块一次调用、块间独立，状态在 `40-outline/_state.json`，键是块标签，已算好的块直接复用。
  **为什么**：933 章的梗概按 48 字算约 4.5 万字 ≈ 4.3 万 token，单次调用塞得下，但一次性喂进去有两个问题：长输入里的细节会被忽略，任何一处失败就得整本重跑。
  **不这么做会怎样**：一次调用失败全盘重来；或者细节被吞掉，大纲只剩几个大词。
- **做法**：缺梗概分成三种成因——「未跑标注」「标注失败」「梗概缺失」——每种都带一句「该怎么办」。判断一章到底成没成，看模型轨字段抽查填了几个（阈值 3）：记了 `errors` 不等于失败，别的字段都填上了、只有梗概是空的，那是梗概后来丢了。
  **为什么**：实测 500 章的梗概是被演示模式整批覆盖清空的——既不是没跑标注、也不是标注失败，按那句「没跑过标注或标注失败」去重跑标注根本补不回来。
  **不这么做会怎样**：三种缺法混成一句「缺 500 章」，看的人只能猜，也就不知道该改哪一项。
- **做法**：块标签先判章号单调性：`b > a` 才写「第 A-B 章」，单章写「第 A 章」，否则退回 `章节 id → 章节 id`。
  **为什么**：番外 / 第二部常常重新从第 1 章编号，这时「第 A-B 章」会写成「第 151-3 章」，甚至退化成「第 1 章」——一个跨了 50 章的分块被标成单独一章。
  **不这么做会怎样**：标签同时是续跑缓存的键和产物里的小标题，写错就既认不出缓存，也读不懂产物。
- **做法**：某块的返回里没有 `summary` 就记 `error` 且**不落盘**（重跑会重试），也不伪造一个空梗概；全书归约只用可用的块，并在 `_meta` 里记 `blocks_used` / `blocks_failed` / `missing`；一块都没成功就直接报「没有一块成功，无法汇总全书大纲」。
  **为什么**：失败不落盘，下次重跑才修得回来；缺口要能被量出来。
  **不这么做会怎样**：一个空串混在段梗概里，被当成「这一段本来就这么简略」，缺口就永久消失了。
- **做法**：输出预算起点取模型声明的 `max_output`（封顶 32000），截断就翻倍重试，加到上限还断才从截断处抢救并标 `salvaged`；费用估算用的是同一个预算数字。
  **为什么**：旧版写死 1200，全书归约的正文还没写完就被砍，报出来却是「返回内容不是 JSON」——截断的 JSON 必然不是合法 JSON，这句文案把病根盖住了，还让人以为是模型不守格式。
  **不这么做会怎样**：11 段梗概全部成功，最后一步白跑；预估费用也按一个早被证明不够用的数字报给你。

**验证**

```bash
python tests/test_outline.py
```

十四个用例：没有梗概时明确报缺原料（`ready=False`、不出大纲、错误列非空）；只跑了一部分标注时说清缺多少；
三种缺梗概成因分得开（被误覆盖的那章归到「梗概缺失」而不是「标注失败」），每条都带「该怎么办」；
8 章按 3 章一块切成 3 块、有单价才算得出费用；分块归约 + 全书归约产出大纲与 `_meta`；
归约失败的块带 `error` 而不是空串、其余块够用时仍能出大纲；章号回落时标签退回章节 id；
断点续跑只重算缺的那块 + 一次全书归约；全书归约截断时预算 1200→2400 拿到完整大纲；
预算加到顶仍截断时保住截断前的字段；普通文字不被误判成截断；
抢救出来的大纲在 `_meta`、`errors` 和 Markdown 里都标出来；Markdown 各小节齐全、`latest.*` 落盘正确；
P22 原语的 schema 与校验（超长不截断——48 字上限曾把半句话砍进大纲原料）。

## 改写台

**做什么**：M3 重写 + M4 一致性校验。按五类指令（改视角 / 扩写 / 精简 / 调节奏 / 强化动机）让模型重写一章，
落下改写稿和一份纯脚本的六类校验；有阻断级问题时「接受」会被接口拒绝。原稿不动，接受只是多一份新版本文件。

**用法**

```bash
# 只能走界面：本模块没有命令行入口
python run_server.py            # 起本地工作台，界面在浏览器里
```

界面：作品页顶部子导航点「改写台」（`#/work/{作品名}/rewrite`）。选章节 + 指令 + 可选补充说明 →
点「改写这一章」→ 确认框里写明章节、指令与「会调用模型、产生费用」→ 确认后左边原稿、右边改写稿，
下方是校验明细（有阻断项时默认展开）。

验收：全通过时显示「六类校验全部通过，可以接受」；有阻断项时显示哪几类，并说明「接受」会被拒绝。
同卡片上还有「接受改写（写新版本）」「强制接受（改坏也认）」「重新改写」三个出口。
注意界面顶栏「使用说明」里的费用提示只列了逐章标注与实体统计，改写台其实也调模型——以改写台自己的确认框为准。

接口

```
GET  /api/works/{name}/rewrite/plan                                  指令类型 + 章节列表（免费，不调模型）
POST /api/works/{name}/rewrite/start {chapter_id,directive,instruction,model}   执行改写（花钱）
GET  /api/works/{name}/rewrite/{chapter_id}                          改写记录（含原稿与改写稿正文）
POST /api/works/{name}/rewrite/{chapter_id}/accept {force}           接受，写新版本
```

**方法**

- **做法**：原稿与改写稿存在同一条记录里（`30-rewrite/{chapter_id}.json`，另写一份 `latest.json`）。
  **为什么**：作者要对成品负责，覆盖正文等于把「改之前长什么样」永久丢掉。**不这么做会怎样**：一次改坏的「精简」把伏笔删了，
  原稿已经没了，既没法对比也没法回退。
- **做法**：「接受」不去改 `00-ingest/chapters/` 里的原稿，而是写一份新版本
  `30-rewrite/versions/{chapter_id}.{时间戳}.md`，并把 `accepted` / `accepted_at` / `version_file` 写回记录。
  **为什么**：留痕不是审计洁癖，是要让人看得出这一章被改过几次、每一次存在哪。
  **不这么做会怎样**：多轮改写之后分不清正文是哪一版，想找回来只能重新花钱跑一遍。
- **做法**：六类校验（V1 长度 / V2 人称 / V3 风格 / V4 结构 / V5 情节锚点 / V6 伏笔线索）全部纯脚本，零模型成本。
  **为什么**：改写那一步已经花过钱，校验再花一次是浪费；而且脚本判据能解释——每条问题都带具体数字、人名或线索描述。
  **不这么做会怎样**：只能人工拿两份稿子逐句对照，上千章的工程量不现实。
- **做法**：严重度分三档，`high` 阻断接受，`medium` / `low` 只提示。判 high 的都是事实损坏：
  丢 K1 里的关键实体（V5）、丢标注里动作是「推进 / 回收」的伏笔线索（V6）、人称从原稿的一类变成另一类（V2）、
  长度超出 0.2–5.0 倍（V1）、改写稿没有段落内容（V4）。**为什么**：这些一旦进了正文就不是风格偏好。
  **不这么做会怎样**：闸门退化成一排永远可以划掉的黄条，等于没有闸门。
- **做法**：G2 输出闸门——`validation.blocking` 非空时 `accept` 直接 400 并说明原因；界面另有
  「强制接受（改坏也认）」走 `force: true`，会把 `force_accept` 写进记录。**为什么**：拒绝要有出路，
  但出路必须留痕，「我知道有问题还是接受」和「我不知道有问题」事后必须分得开。
- **做法**：V3 只在作品自己声明过 `style_checks` 时才有基准（且排除 `perspective` 一类，人称归 V2）；
  精简 / 扩写把长度区间放宽到 0.2–5.0，其余指令 0.5–2.5；风格违规 1 处 low、2 处 medium、3 处及以上 high。
  **为什么**：没声明过的风格约束不存在「违规」，主动改长度的指令也不该被长度判据拦住。
  **不这么做会怎样**：满屏假阳性，真问题被淹没。

**验证**

```bash
python tests/test_rewrite.py
```

跑在临时根目录 + 本地 MockServer 上，不发真实请求。覆盖：plan 返回 5 种指令与章节列表；执行一次改写后
记录里同时有 `original` 与 `rewritten`、`30-rewrite/{章节}.json` 落盘；接受后 `versions/` 里恰好 1 个版本文件，
并且**回读原稿确认逐字未变**；造一份带 V4 阻断问题的记录，`force:false` 必须 400 且文案里有「阻断」，
`force:true` 才通过；不存在的章节、不存在的作品都给 400 而不是 500。

## 题材规则库

**做什么**：L2 题材规则（M6）。把作品登记到题材（`genres/_index.yaml`），再把同题材各部作品知识库里的
指纹（`20-kb/k3-fingerprint.json`）按指标聚合成题材规则，落盘 `genres/{题材}/rules.json`。纯脚本，不调模型。
同题材作品不足 3 部时不产规则，只标「样本不足」。

**用法**

```bash
# 只能走界面：本模块没有命令行入口
python run_server.py
```

界面：顶栏「题材与对比」（`#/genres`）。「作品 → 题材登记」表里，下拉选一个已有题材，或者在右边填一个新题材名——
两个控件互斥，选了下拉会清空输入框，按钮只在登记真的会变时才可点；选「（不登记）」再点按钮就是取消登记。
「L2 题材规则库」表按题材显示作品数 / 样本足不足 / 是否已聚合，点「聚合」出规则表（规则 id、内容、命中率、置信度）。

接口

```
GET  /api/genres                       作品 → 题材映射 + 各题材状态
PUT  /api/genres/assign {work,genre}   登记（genre 传空串 = 取消登记）
GET  /api/genres/{genre}               已聚合规则（没有则 404）
POST /api/genres/{genre}/aggregate     聚合（纯脚本）
```

**方法**

- **做法**：聚合的对象是「同一指标在多部作品里的取值」，原料是每部作品知识库里已经算好的 L3 条目，
  不重新调模型。**为什么**：题材规律是统计出来的，不是问出来的；再用模型读一遍全书既贵又不稳定。
  **不这么做会怎样**：同一题材聚合两次得到两套措辞不同的规则，落盘文件之间无法比较、无法复算。
- **做法**：只聚合代码认识的两类指标——评分类（`hook_strength` / `emotion` / `conflict` / `info_release` /
  `mainline_progress` / `motive_strength`，取均值）与主导类（`hook_type` / `perspective`，取分布众数）。
  **为什么**：口径必须跨作品一致，否则「均值」是个没有意义的数字。
  **不这么做会怎样**：把不同口径的条目混进同一个 mean，规则看着有数，其实是编出来的。
- **做法**：作品数 <3 不产规则，返回的 `note` 明写「样本不足」；置信度按作品数分档——<3「低（样本不足）」，
  3–9 最高「中」，≥10 且命中率 ≥0.8 且极差 ≤1.5、或 ≥15 且命中率 ≥0.9 才给「高」。
  **为什么**：单部作品的特征不能当题材规律，把 n=1 的均值标成「高」正是这个项目一直在防的静默失效。
- **做法**：命中 = 作品值与题材均值差 ≤0.8（1–5 量表一格以上才算偏离），命中率、极差 `spread`、
  逐作品取值 `per_work` 都写进规则里。**为什么**：规则要能被反驳——有命中率和逐作品取值，
  才看得出这条是不是被一两部作品带偏的。**不这么做会怎样**：只剩一句「均值 3.8」，谁也没法判断该不该信。
- **做法**：聚合顺带产出 `baseline.means`（各指标均值 + `n_works`）给 M8 用；`_index.yaml` 先写
  `.yaml.tmp` 再 `replace` 覆盖。**为什么**：跨题材对比必须用聚合后的题材均值，不能随手挑一部作品当代表；
  登记表半截写坏会让整张映射读不出来。
- **做法**：列表接口同时给 `work_count` / `sample_ok` / `rules_ready` 三个状态，而不是一个「有规则」的布尔。
  **为什么**：界面上「登记了 2 部」和「能出规则」是两件事。**不这么做会怎样**：用户点了聚合看到空表，
  只能猜是没数据还是坏了。
- **做法**：规则 id 固定成 `L2-{题材}-{指标}`，规则按命中率降序、同率时按 id 排；规则正文是给人读的一句话
  （「该题材作品 章末钩子强度 均值集中在 4.0」）。**为什么**：界面和测试都靠 id 定位某一条规则，措辞会变，id 不能变。
  **不这么做会怎样**：改一次文案就找不回「上次那条规则」，跨次比较只能靠人肉对照。

**验证**

```bash
python tests/test_genre_lab.py
```

（这一份同时覆盖下面三节，手工造指纹，不跑知识库。）这里覆盖：登记后 `/api/genres` 的映射里有这笔，
空串能取消登记；只造 1 部作品的题材去聚合，`rules` 必须是空数组**且** `note` 里明写「样本不足」（不许静默成功）；
造 4 部同题材作品后聚合，出 `L2-玄幻-hook_strength` 规则、带命中率、`works` 按名字排序、
`genres/玄幻/rules.json` 落盘。

上游依赖也断言过：题材库吃的是 KB 的 K3 指纹，而 K3 标注不足 5 章就是 `available:false` 并说明原因——
见 `python tests/test_kb.py`。

## 对比分析器

**做什么**：M8。一次构建出三份报告——同题材对比（同题材每部作品 vs 题材基线）、跨题材差异
（同一指标在不同题材间的分布，按跨度从大到小）、作品 vs 基线偏离度（偏离 >0.8 的指标，
即这部作品哪里「不像这个题材」）。原料是各作品的 `20-kb/k3-fingerprint.json` 与题材库
`genres/{题材}/rules.json` 里的 `baseline`，纯脚本，不调模型。

**用法**

```bash
# 只能走界面：本模块没有命令行入口
python run_server.py
```

界面：顶栏「题材与对比」→「M8 对比分析」，选一部作品 + 一个题材，点「生成对比报告」。三块结果一次出：
同题材表格（一行一部作品、一列一个指标）、跨题材差异（界面只列跨度前 10）、偏离度
（没有超过 ±0.8 的指标时明说「作品贴合题材基线」）。重新进页面会读最近一次报告。

接口

```
GET  /api/compare                       最近一次报告（没跑过 exists:false）
POST /api/compare/build {work,genre}    构建三份报告
```

**方法**

- **做法**：三份报告各自独立、都可解释，一次请求出全，落盘 `compare/latest.json`。
  **为什么**：对比的价值在于两个方向一起看——只看同题材不知道这部作品是不是本来就该这样，
  只看跨题材不知道具体是哪部作品偏了。**不这么做会怎样**：得点三次、看三个页面才能拼出一个判断。
- **做法**：同题材报告的行来自每部作品的指纹均值，基线直接读题材库 `rules.json` 里的 `baseline.means`。
  **为什么**：基线是 N 部作品聚合的结果，比挑一部「代表作品」稳。
  **不这么做会怎样**：换一部代表作品结论就变了，而界面上完全看不出这件事。
- **做法**：跨题材只用已经聚合出 `rules.json` 的题材，且某个指标至少要有 2 个题材有值才进对比，
  `spread = max - min`，按跨度降序。**为什么**：单个题材的「分布」没有意义；跨度排序把最能区分题材的指标顶到最前。
  **不这么做会怎样**：拿单题材的指标出来比，得到一堆恒等于 0 的差异项，还占着表格。
- **做法**：偏离阈值 ±0.8（1–5 量表约一格），每条列出 `work_mean` / `genre_mean` / `delta` / 方向。
  **为什么**：这个 0.8 和 M6 的命中判据是同一个口径——同一个量表里两套阈值迟早互相打架。
  **不这么做会怎样**：题材规则说这部作品「命中」，偏离报告说它「偏离」，用户只能挑一个信。
- **做法**：缺前置时返回 `available:false` 加一句 `note`（作品还没有 L3 指纹 / 题材还没聚合规则 / 题材基线为空），
  而不是给一份空报告。**为什么**：空表和「没数据」在界面上必须一眼分得开。
  **不这么做会怎样**：用户看到零条偏离，会以为作品贴合题材基线——这正是静默失效。
- **做法**：偏离报告只列数据、不下结论（`note` 原话是「供你判断是风格特色还是问题」）。
  **为什么**：偏离很可能正是这本书的卖点，脚本没有资格把它判成缺陷。
- **做法**：同题材报告的表头只列出真的有值的指标（任何一行有值才进 `metrics`），没有值的指标连列都不出现。
  **为什么**：一列全是「—」的表格看不出信息量，还让人以为这部作品缺数据。
  **不这么做会怎样**：六列里三列是空的，得逐列确认是「没测」还是「没显示」。
- **做法**：同题材报告只收指纹可用（`available:true`）的作品行；书架一部作品都没有时，界面不出对比按钮，
  只说「书架为空，先导入作品并登记题材」。**为什么**：没有作品是正常状态，不是失败，不该弹一个错误框。

**验证**

```bash

```

（与题材库共用一份自检，手工造指纹，不跑知识库。）这里覆盖：`same_genre.genre` 正确、行数 ≥3、
行里带 `hook_strength` 均值；`cross_genre.comparisons` 非空、含 `hook_strength`，
`emotion` 的 `per_genre` 至少跨 2 个题材；`deviation.work` 是传进去的那部作品、每条偏差都是数值；

## 融合器

**做什么**：M5。用已入库作品的自有素材（`20-kb/k1-entities.json` 里的人物 / 地点 / 势力 / 能力）拼一个新故事骨架：
一句话前提、世界元素清单、人物卡片、11 拍三幕节拍表。每条素材都带 `source`（来自哪部作品），
骨架是可编辑草稿，不含正文。纯脚本，不调模型。

**用法**

```bash
# 只能走界面：本模块没有命令行入口
python run_server.py
```

界面：顶栏「题材与对比」→「M5 融合器」，点「生成新故事骨架」。界面这一版不带参数，等于扫描全部已入库作品、
随机种子也不固定，所以连点两次结果不同。产出四块：一句话前提（附素材来源作品列表）、人物表（槽位 / 名字 / 身份 / 来源）、
世界元素表（种类 / 名称 / 说明 / 来源）、骨架节拍表（# / 阶段 / 动作）。进页面会读最近一次的骨架显示出来。

接口

```
GET  /api/fusion                                 最近一次骨架（没生成过 exists:false）
POST /api/fusion/generate {source_works?,seed?}   生成骨架（纯脚本）
```

`source_works` 省略或传空数组 = 扫描 `workspaces/` 下所有不以 `_` 开头的目录；`seed` 传整数可复现同一次抽签
（测试就是靠它固定结果）。

**方法**

- **做法**：素材只从已入库作品的 K1 实体卡片里取，复制每一条时打上 `source: 作品名`。
  **为什么**：这是「融合」和「抄袭缝合」的分界线——能追溯到来源的才叫素材。
  **不这么做会怎样**：凭空生成的「新设定」与任何作品都无关，却顶着「用自有素材生成」的名义落盘。
- **做法**：世界元素固定三个槽（地点 / 势力 / 能力），人物固定主角 + 对手，再加最多 2 个配角（关键配角 / 盟友）。
  **为什么**：骨架要有形状，全随机就成了一份素材清单而不是故事结构。
  **不这么做会怎样**：每次生成的结构都不一样，没法照着往下铺章。
- **做法**：主角从 `role` 不是「路人 / 反派」的人物里抽；对手优先抽 `role == 反派`，没有反派才退而取一个名字不同的人；
  抽不到就留「（待定主角）」这类占位。**为什么**：宁可留空位让人填，也不要假数据——空位一眼看得出，
  编出来的名字要读半天才发现是编的。
- **做法**：节拍表是写死的 11 拍（开场 / 触发 / 建立 / 阻碍 / 深入 / 转折 / 低谷 / 觉醒 / 对决 / 收束 / 回响），
  每拍配一句动作模板，不必调模型。**为什么**：三幕结构是骨架的骨架，让模型写一遍只是换套措辞，还可能漏拍。
  **不这么做会怎样**：每次生成的节拍数量和阶段都不一样，作者得先对齐结构才能用。
- **做法**：一部素材都取不到时直接报错「没有可用的自有素材（先为作品构建知识库 K1 实体卡片）」，接口 400。
  **为什么**：K1 来自实体统计 + 知识库构建，没跑过就是没有素材；返回一份空骨架会让人以为是自己哪里没配对。
- **做法**：落盘 `workspaces/_fusion/skeleton-{时间戳}.json`，同时覆盖一份 `latest.json`。
  **为什么**：保留历史才看得出上一次抽到的是哪套素材，`latest` 只是给界面读的便利文件。
  **不这么做会怎样**：连点两次之后只剩最后一版，第一次的结果无从比较。
- **做法**：节拍的动作是模板句，具体名字只在人物表与世界元素表里出现（节拍本身还挂着一份世界元素清单
  当 `hint`，界面只渲染 # / 阶段 / 动作）。**为什么**：骨架是给人往下铺章用的，模板句好替换；
  要是它直接写成正文腔的段落，作者反而要先把一段假正文删干净。

**验证**

```bash
python tests/test_genre_lab.py
```

（与题材库共用一份自检，手工造 K1 卡片，不跑知识库。）这里覆盖：传 `source_works: ["玄1","都1"]`（`seed: 1`）后
`sources` 恰好是这两部；`cast` ≥2 且**每个人物都有 `source`**；`world` ≥3 且**每个世界元素都有 `source`**；
`beats` ≥10；`workspaces/_fusion/latest.json` 落盘；传一个不存在的作品名必须 400，而不是给一份空骨架。

## 结构体检报告

```
python report_cli.py --work 示例作品            # 出报告并落盘
python report_cli.py --work 示例作品 --stdout   # 只打印
python report_cli.py --demo
```

产出在 `workspaces/{作品}/30-reports/`（Markdown + JSON，另有 `latest.*` 供界面读）。

### 零标注也要能出报告

如果报告必须等全量标注跑完才有，它的价值就全压在「愿不愿意先花一次钱」上。
所以分成两类小节：

| 类型 | 数据来源 | 没有标注时 |
|---|---|---|
| 章节长度、分卷统计、风格违规 | manifest + 标注里的脚本轨，**零模型成本** | 照常出 |
| 情绪、冲突、动机、钩子、爽点、伏笔 | 模型轨标注 | 显式写「无数据」并说明原因 |

**「无数据」必须明写。** 空曲线和「没跑过」在界面上要一眼分得开——
用空数组假装正常，就是又一次静默失效。报告里的每个小节都带 `available` 与 `reason`。

### 自洽性检查（第 ⑦ 节）

两个真实踩出来的检查项：

| 检查 | 为什么 |
|---|---|
| 脚本轨与模型轨**人称不一致**的章节 | 脚本轨是启发式，遇到自由间接引语（第三人称叙述 + 大段「我」的内心独白）会判反。不一致就该列出来让人核对，以模型轨为准 |
| 出现了**多个提示词前缀指纹** | 加字段、改约束都会让 `prefix_hash` 变。前后两批数据的字段口径不同，混在一起比趋势会得出错误结论，而这一点从单个标注文件里完全看不出来 |

### 报告读法

1. **疑似断点**（默认 30 章未推进的未回收伏笔）——最该先看的一节
2. 章节长度的极短章（<200 字，更像切分残留，不是「写得短」）
3. 动机线的弱章（≤2）
4. 风格违规按规则聚合，可下钻到章节

1-5 量表字段实测有 ±1 噪声，**看分卷均值与趋势，别拿单章精确值下结论**。

### 三条设计约束落在实现里

| 约束 | 落实方式 |
|---|---|
| **导入必须两步** | `upload` 只切分不落盘；`commit` 才写入。测试里有断言：预览阶段磁盘上不能出现作品目录 |

| **文件系统是唯一真相源** | 不引入数据库、不做内存缓存。书架与概览每次现读 `manifest.json`，界面看到的和脚本读到的一定是同一份 |

### 关于「不泄露正文」

那条约束只针对**导入预览**：文件还没确认归属时，接口只给统计与标题。
作品导入完成后它就是你自己机器上的数据，读正文是最正当的用法。

`test_server.py` 覆盖：界面文件可达、书架与概览的数值同清单一致、分页与筛选、路径穿越拦截、
**预览不落盘 / 确认才落盘**、重复提交被拒、非法 token、空文件、坏模板显式报错、错误形状统一。

`test_ui_smoke.py` 覆盖接口测试抓不到的一类问题：**真的点按钮**。它会在同一个页面会话里
连做两遍完整导入——「按钮点了没反应」这种故障只在第二遍才暴露。任何未捕获的 JS 异常、
任何 console error 都算失败。

```bash
pip install playwright && playwright install chromium
```

playwright 升级后自带的 Chromium 版本号会跟着变，重新下载一次很慢。
测试会自动退回到本机已有的 Chromium / Edge / Chrome，装不上也能跑。

### 踩过的坑：三次「点了没反应」

| 现象 | 根因 | 修法 |
|---|---|---|
| 确认导入无响应 | 全局 `imp.busy` 在成功分支没复位 | 删掉这个模式，改用 `withBusy()`，`finally` 里复位 |
| 开始切分预览无响应 | 同一个标记还卡着，吞掉了页面上**之后所有**按钮 | 同上（第一次只修了一半） |
| 导完一部再点「导入作品」没反应 | hash 未变 → 不触发 `hashchange` → 路由不重跑，停在上一部的完成页 | 加 `imp.finished`，并在标签上补一次手动渲染 |

共同点：接口全对、页面看起来正常（按钮是亮的、无报错），只有真人点一下才会发现。
所以除了修，还要有测试兜住——并且**错误必须显形**（页面顶部 `showFatal` + 全局
`error` / `unhandledrejection` 监听），不能只躺在 Console 里。

### 设置页：服务商与密钥

`#/settings`。填密钥、测试连接、看定价，不用再手改 `providers.yaml` 和 `.env`。

**密钥永不回显**：界面只显示「已配置 / 来源 / 后 4 位」，输入框永远是空的，
接口响应体里也不会出现明文。

**写入策略：写回当前真正生效的那一个来源。**

读取优先级是 环境变量 > `.env` > `secrets.json`。如果固定写 `secrets.json`，
而 `.env` 里已经有一条更旧的同名键，读的时候仍然是 `.env` 那条——
界面报「保存成功」，调用却依然 401，且没有任何提示。这正是本项目反复防的静默失效。

所以：

| 当前来源 | 保存时写去哪 | 说明 |
|---|---|---|
| 环境变量 | **拒绝** | 优先级最高，界面改不了，要明说而不是假装成功 |
| `.env` | 写回 `.env` | 顺带把粘进来的 `$env:KEY=` / `export KEY=` 规范掉，其余行原样保留 |
| 没有 / `secrets.json` | 写 `config/secrets.json` | |

写完立刻回读一次确认——**写不进去却报成功，比不写还糟**。

**测试连接**只发一句合成测试文本（`端点与鉴权` → `模型名` → `最小对话`），
不碰任何作品原文；失败时给出错误类别与下一步该怎么办。另有「完整探测」跑 P1-P5 并存档。

### ⚠️ 不要用原生 confirm() / alert()

实测：`sandbox` 里**没有 `allow-modals`** 的 iframe 会把 `confirm()` **静默变成 `false`**——
不弹窗、不报错、不发请求。用户看到的就是「点了没反应」，控制台一片安静。
内置预览面板就是用 iframe 渲染页面的，所以这个坑一定会踩到。

所以界面上所有确认都走页面内的 `askConfirm()`，它顺带解决另外两件事：
原生对话框里放不下成本明细（而「启动前必须展示范围与成本」是既定原则），
而且它阻塞主线程、不可样式化。

`test_ui_smoke.py` 里有一条专门的回归：把页面塞进 sandbox iframe 再点一次。

## 测试的安全铁律（真实事故换来的）

真实事故：冒烟测试里「移出书架」点的是 `[data-archive]`——**页面上第一个匹配**。
某天书架上有用户的真实作品，第一个匹配就是用户的书，测试把它移进了归档。
（归档是移动不是删除，书已完整恢复，但事故就是事故。）

所以本目录的测试遵守两条铁律，缺一不可：

1. **不许假设书架为空** —— 用户随时可能有真实作品。能守的约定只有
   「测试自己造的作品，在导入前不许出现」
2. **UI 操作必须按测试作品的名字定位** —— `[data-archive="{测试作品}"]`、
   `locator(".work-card", has_text=...)`，绝不许「第一个」这类泛选器

接口层同样的病是反向的：早期断言「书架里应该有某部作品」「书架必须为空」，
数据一变就假红。现在改成「列表里每一部在磁盘上都有对应产物」（抓幽灵作品）+ 按名字找。

除此之外，**整套测试跑在一块临时根目录上**（`server_main.PATHS`），从根上不碰真实
`workspaces/`。但第 2 条不能因此省掉：位置判据本身就是脆的，隔离只是多一层保险。
